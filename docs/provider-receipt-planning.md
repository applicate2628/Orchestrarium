# Provider receipt planning contract

This is the source contract for `scripts/installation/receipt_plan.py`, the first pure part of the existing document/managed-instruction ownership work. It reuses the SDK `ownership.py` and `configuration.py` contracts and the same provider receipt identity. It is not a second installer, a durable binding protocol, or a live migration command. The installer imports the shared pure contracts for Codex and Claude preparation. It bootstraps an absent provider receipt from positively received fresh payload-file creations. Explicit exact-current selections can also replace selected Claude instruction files or a Codex document span and update their receipt entries, without treating old receipt hashes as historical authority. Automatic receipt-driven updates, removal and document adoption remain disabled.

## Inputs and results

`plan_changes(receipt, provider, scope, outcomes, document_context)` accepts exact prior receipt bytes or explicit absence, artifact byte preimages, proposed rendered outcomes, and the existing bundled Markdown context function. File payloads and document blocks share one plan. Each immutable artifact result contains its route, exact before/after SHA-256 fingerprints and outstanding acquisition requirements. Changes contain only validated file/config entry deltas, not a serialized receipt.

- An unrecorded ordinary update stays on the legacy route and acquires nothing, even if its resulting content contains familiar markers.
- An ordinary update or removal of a claimed artifact must match its recorded semantic digest. Missing, changed or ambiguous content is preserved without changing its entry or falling back to legacy overwrite.
- A positive creation outcome may propose ownership only for a new file or a newly inserted block that leaves all original text intact.
- Adoption must select the exact current artifact bytes. Marked blocks retain exact outside slices; unmarked Codex adoption additionally selects a reviewed, line-bounded span under the existing SDK boundary contract. The digest and span are not user consent.
- Update and removal of a claimed document preserve exact outside text. File payload digests remain byte-exact. Other legacy artifacts are not blocked merely because a receipt exists or a different artifact is preserved.

`apply_delta(receipt, plan)` produces only an in-memory validated record projection. It rechecks the exact input receipt fingerprint, including JSON whitespace, and preserves unrelated files, directories, configuration entries and the presence/value of `layout`. A previously absent record has no layout injected. The function performs no filesystem write, serialization or publication and grants no authority to perform them. Public dataclasses are constructible: this projection validates schema/currentness, not provenance that `plan_changes` produced the supplied plan. Integrations must retain the original `Outcome`, exact adoption boundaries and separate approval evidence, rather than authorize using plan fingerprints or requirement strings alone.

`serialize_delta(receipt, plan)` validates the projection and returns candidate bytes using the common codec's `serialize_record`, which preserves layout presence/value and enforces the existing 4 MiB encoded limit. A no-op retains the exact original bytes or absence. The original `encode_record` still constructs its existing copy-layout record; both entry points share one serializer. Candidate bytes are neither persisted ownership nor permission to write.

## Compatibility and integration boundaries

The common SDK encoder currently asserts `provider-owned-copies-v1`. This hotfix has not established that layout, so the planner deliberately does not call it. No v1 field extension, new receipt schema, installation UUID or claimed persistent identity is invented here. The reused client metadata differs only in the pre-SDK Claude source/reference paths; it does not activate another host or provider.

A matching v1 digest proves only a semantic match at its logical name. It does not prove historical physical-root continuity. Every recorded proposal retains that outstanding requirement. Fresh/adoption proposals retain acquisition and exact user-approval requirements. All changes still need current artifact and receipt inputs and one atomic commit/rollback through the existing transaction owner. The plan is not a capability, and callers must not clear those requirements by trusting flags, labels or the plan itself.

Before any live integration, one owner must bind receipt and target inputs, receive actual production outcomes, preserve currentness through content-plus-receipt commit, and share the resulting record with repeat install, update and uninstall. Serialization and truthful layout are covered only as pure byte operations here. The existing transaction's commit flag and exception recovery do not establish crash-atomic multi-file publication. Link retargeting, identity reuse and filesystem-chain safety remain separate unresolved gates. Pure tests do not qualify those operations or waive their restrictions.

The general receipt planner is not enabled for automatic updates or removal. Fresh-file bootstrap and the explicit selected-current replacement routes below are connected. This is not a fix claimed complete or a reason to archive the existing ownership tickets.

## Exact document outcomes and provider preparation

The pure document_outcomes.render_documents adapter accepts the complete provider document preimage set and the existing producer as a caller-supplied pure callback. It retains original UTF-8 bytes separately from renderer input, returns immutable proposed outputs, and never reads or writes a target. Codex receives exact text; Claude receives its current universal-newline view. That normalization is disclosed, not misrepresented as preservation of the raw preimage.

All document inputs are validated and decoded before rendering. Both Claude documents must render successfully before a result tuple is returned. This is an all-or-error in-memory result, not atomic storage publication; callback purity remains a caller obligation. The callbacks must use the existing producer owners, not a competing renderer.

Conversion to the existing planner always uses update intent. Neither an absent preimage, familiar markers, nor successful rendering is a positively received creation or adoption event. The adapter does not select adoption spans or grant permission. Exact bytes remain available for the planner to reject an outside-text change, including current Claude newline normalization. Public result dataclasses are not trusted capabilities.

Codex preparation now uses the common adapter. The read-only _prepare_codex_agents function retains the previous source-read and exact-newline target-read order, and returns a DocumentResult before any write. Its project_scope argument selects logical metadata: project AGENTS.md or global .codex/AGENTS.md; it does not infer authority from the physical path. The existing _merge_codex_agents wrapper calls preparation once and retains its warning, dry-run, writer and None-return contract. The writer still receives the same rendered text through the existing owner. Preparation results are proposals, not observed writes or capabilities.

Claude preparation now uses the single-document render_document adapter. It validates the logical path against the provider/scope map and shares decoding/rendering helpers with the batch API. The batch API still validates and decodes its complete input set before any callback; the single-document API lets _prepare_claude_docs retain the existing sequence: read and validate sources, read/render CLAUDE.md, then read/render AGENTS.md. Both immutable proposals are returned before the wrapper can write either. The wrapper retains its None return, dry-run output and Claude-first writer order. Exact input bytes are retained while the existing universal-newline renderer view remains unchanged. project_scope selects logical scope explicitly; neither an absent input nor a successful render acquires ownership. Document receipt planning/persistence, historical storage authority, physical creation receiving, coupled writes and repeat lifecycle acceptance remain future work under the existing restrictions. Tests use AST-isolated source functions and memory-only input transport with the real pure adapter/parser, never a full installer import or physical-chain execution.

## Existing transaction-derived receipt outcomes

The existing Lead finalizer and ordinary non-Lead tuple receipt verification share _admitted_tree_manifest. For enabled transactions it reads included payload bytes through the admitted/composed image using the existing _image_file_bytes reader. It retains the existing no-follow manifest traversal and runtime-cache exclusions. Lead compares that manifest with the admitted stage minus exact proven reclamations, then hashes the same compared manifest using the existing tree-manifest codec. Non-Lead tuple verification compares the returned manifest with its already selected receipt entry before the existing serialization/writer. It does not change managed-member selection, retained unselected entries, legacy-entry refusal or receipt schema.

The pure _canonical_lead_expected_manifest helper preserves the prior reclamation calculation. Lead dry-run returns before manifest work; non-Lead tuple verification remains under its existing not-dry-run guard. Disabled direct-operation transactions retain the existing default reader rather than gaining a new full-image census. Receipt format, no-op handling and create/replace writers are unchanged. These are connected improvements to existing receipt producers, not provider-receipt persistence or proof of historical root identity.

The managed-member postcondition also binds included payload reads to its existing composed current image when an enabled transaction is present. This image retains the function's original, migrated, effect and creator witness checks; it is not replaced with the generic transaction snapshot. Calls without a transaction, including both projection validators, and disabled direct-operation transactions retain their existing default reader. The existing before-state return, cache exclusions, expected-manifest construction and final comparison are unchanged. The callback uses the existing file-identity/content refusal behavior; no new exception translation or ownership claim is introduced.

Qualification of this change is limited to pure manifest semantics, static source wiring and independent source review. The shared reader, receipt producers, physical image reader, complete directory/chain custody, cache races, transaction settlement and rollback have not been executed or qualified by those checks. Their existing restrictions remain in force; pure tests must not be represented as live lifecycle acceptance.

## Fresh payload receipt bootstrap

When the selected provider receipt is absent, the installer admits that leaf to the existing transaction and tracks successful explicit fresh branches of ordinary copy, byte-write and create-file operations. The witness retains the actual completed file node plus the owning anchor and parent identities captured before creation. Failed operations, equal-byte no-ops, preexisting files, replacements, trees and migrations do not become fresh-file claims. Linked owners are excluded rather than assigned an inferred logical mapping.

The finalizer runs after the existing Lead receipt and before transaction.commit. It selects only provider payload paths, excluding documents/configuration, runtime caches, temporary custody and the receipt itself. It reuses serialize_record through serialize_fresh_payloads without adding layout, configurations or directories. On the default route, existing receipts, including invalid records or other leaf types, are preserved without decoding or merging. A receipt that appears before or during admission is not adopted.

The receipt is created by the same mutable owner. A successful fresh-creation witness is required even if create_file could otherwise return an equal-byte no-op. Payload witnesses are checked before and after receipt publication, and the receipt is read back through its bound file witness. Failure before commit enters the existing transaction recovery path; no new inverse, deletion participant or rollback owner is added. This is exception-coupled recovery, not crash-atomic multi-file publication or a guarantee of successful recovery under identity drift.

Qualification is pure codec/filter behavior and static wiring review only. Physical writer, receipt publication, directory-chain, race and recovery execution remain unqualified under the existing restrictions. Historical storage continuity, repeat update/removal, existing-receipt refresh and document ownership remain open. An unchanged or matching receipt is not newly granted authority.

## Explicit selected-current Claude replacement

The repeatable --replace-claude-instruction PATH=SHA256 option selects existing source-listed Claude instructions for this invocation: agents/NAME.md at the top level or commands/...md. PATH is provider-relative, while the receipt key is explicitly .claude/PATH relative to the project or home. The digest selects the reviewed current file bytes; it is not evidence of historical ownership. No grant is inferred from a source name, matching receipt, source equality or --force. Omitting the option retains existing instruction preservation.

For instruction files, the shared planner's replace intent requires before/after bytes, the exact current selection digest, no document span, separate current-replacement approval and selected-storage acquisition. It can replace a stale file claim without treating that claim as authority. Existing update/create/adopt/remove semantics and schema, category and alias checks remain. The common serializer preserves unrelated receipt entries and existing layout presence/value.

All selections, source bytes, target beforeimages and receipt input are validated before content writes. Selected linked/reparse subroots and nonordinary files are outside this route. Invalid or incompatible receipts block only the requested selected operation; the default route continues preserving them. Selected instructions reuse replace_exact_file under the existing transaction. Equal intended/current bytes need no content write, but any receipt acquisition still depends on the explicit current selection and binding.

The finalizer receives every selected outcome, rechecks sources and actual target bytes, combines eligible fresh creations through the same planner, and writes one receipt before commit. Every combined outcome must have its expected proposal route. A conflicting old claim for a freshly recreated unselected file therefore fails the explicit selected batch before receipt publication and enters existing transaction recovery; it is never silently retained with a stale digest or treated as historical authority. This does not alter the default preservation route. An absent receipt still requires a positively received new creation; an existing receipt is replaced only against its exact bound preimage. Payload and receipt readback are rechecked after publication. Existing recovery remains the sole inverse owner. Neither this source integration nor its pure/static checks qualify physical replacement, directory-chain safety, race behavior, exception recovery, crash atomicity or later automatic update/uninstall.

## Shared selected-document rendering

The pure configuration component now shares one exact-current document selection validator between the selected renderer and the receipt planner's legacy-span check. The digest is SHA-256 of the complete original UTF-8 document, without newline normalization. The span uses Python string character offsets into that exact decoded text, not UTF-8 byte offsets. These caller-supplied values are preconditions, not consent or historical storage authority.

For a marked document, the selected span must equal the single parser-visible managed frame. Literal end markers inside closed Markdown examples do not truncate that frame. Incomplete, ambiguous or code-hidden framing refuses without falling back to a raw end marker. An unmarked selection is allowed only for Codex, using the existing SDK line-boundary, code-span and legacy-heading contract. Boolean or non-integer offsets and a boundary splitting CRLF are invalid.

The selected renderer builds a fresh frame through the existing shared merger, replaces only the validated span, preserves the exact outside prefix and suffix, and revalidates the resulting frame in its surrounding document context. Marked replacement retains the old outside newline bytes; unmarked legacy replacement includes the fresh frame's terminal LF. Invalid source payloads or a frame swallowed by surrounding code refuse.

The explicit Codex selection route below now uses this helper. The ordinary Codex renderer retains its compatible raw-END behavior, and document adapters still produce update-only outcomes. Existing claims still refuse adoption. A separately selected Codex block replacement requires the full current preimage and span, verifies exact outside slices, and couples content with receipt publication through the existing owner. It does not acquire historical authority or qualify physical lifecycle behavior.

## Explicit selected-current Codex document replacement

The single --replace-codex-document SHA256:START:END option selects a reviewed interval of the current Codex document for this invocation. The logical path is AGENTS.md for project installs or .codex/AGENTS.md for global installs. The digest covers the complete raw UTF-8 document, including outside text and original newlines. START and END are canonical nonnegative ASCII decimal Python-string character offsets, not UTF-8 byte offsets, UTF-16 code units or line numbers. Repeated options, stale digests, invalid spans or non-Codex use refuse. No selection is inferred from --force, markers or receipt presence.

A marked selection must be exactly the sole parser-visible managed frame, excluding its outside line ending. An unmarked Codex selection uses the shared SDK legacy-span contract. Closed examples containing a literal END do not shorten the selected frame. Malformed or ambiguous selection never falls back to the ordinary raw-END renderer. The default no-selection route remains unchanged.

Preparation binds the ordinary destination's admitted preimage and parents, captures both source Markdown files with exact raw-byte witnesses, and renders their established universal-newline text view through the common strict renderer. The block replace outcome includes the exact selection digest and span. It may replace a stale config claim as a new selected acquisition; adoption still cannot override an existing claim, and no old digest is treated as historical authority. The common selected batch preplans one receipt before content writes, uses the existing exact-file writer, verifies actual afterimages and both source witnesses, and finalizes content and receipt within the existing transaction. Project installs retain the same complete UTF-8 document budget warning.

Existing receipts retain full parent and raw-preimage binding. For an absent receipt, parent evidence reuses covered original snapshot entries, including known absence; parents outside that coverage are bound at selection preflight. Empty leaf snapshots never invent parent absence. A missing parent that later appears must satisfy the existing transaction creator-proof checks. Receipt creation requires a unique new fresh-file witness and exact readback, with original parent evidence rechecked. The mutable receipt is not registered as a read-only dependency. Unrelated receipt entries and layout remain preserved semantically.

Selected symlink/reparse or other nonordinary document routes are outside this acquisition path. Preflight conflicts refuse before content writes; later binding or combined-receipt conflicts enter existing recovery. The physical writer, directory-chain, race and recovery behavior has not been executed or qualified by this source integration and its pure/static tests. Historical automatic updates, general adoption, uninstall and release acceptance remain open.

## Terms and Abbreviations

- Provider receipt: the version-one Orchestrarium record of claimed artifact paths and content digests.
- SDK: Software Development Kit; here, the existing SDK integration branch supplying the shared source contracts.
- SHA-256: Secure Hash Algorithm with a 256-bit digest; a content fingerprint, not proof of consent or storage identity.
- Legacy route: the existing update path for an artifact without a claimed receipt entry.
- Projection: an in-memory record after applying validated entry changes, without filesystem mutation.
- Layout: the receipt's claim about the installation arrangement; its absence must not be converted into a claim.
- Storage authority: independently established permission and identity continuity for the actual target, beyond its logical path or matching bytes.
