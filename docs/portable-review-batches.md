# Portable review batches

`publication_review_policy.materialize_portable_review` prepares one existing native-bound policy record from an explicitly portable, owner-received reviewer decision. It does not write policy or authenticate JSON labels. Use the existing `promote_decision` preview/apply path and mandatory authorization.

The decision has exactly `schema` (`orchestrarium.portable-review.v1`), `project`, `scope` (`native-repository-content`), and `record`. Project contains exact opaque `provider`, `authority`, and provider-issued immutable `repositoryId`. The record is the existing active initial record body without `repository` or `recordSha256`; all occurrence, content/context/detector, commit, report and revocation conditions remain unchanged. A batch may contain many ordered unique occurrences; it is not a whitelist.

The admitted owner must obtain the accepted decision digest from the actual reviewer decision, independently resolve the same immutable project identity through the authenticated provider, and capture the current native repository using existing queries. The observation must be bound to this selected repository and its admitted publication route, not merely an unrelated successful provider lookup. Neither a matching remote URL, a repo-controlled file, a claimed role nor copied Git objects authenticates project identity or approval. Pass SHA256(C(decision)) as received_decision_sha256. Values must come from the owner's actual trusted inputs, not be computed from an arbitrary submitted document and treated as approval.

Stable record IDs bind logical decision ID plus project plus native repository. Exact replay is idempotent; a different or revoked existing record is refused, not overwritten. Always supply the current record when available and use normal document/record preimage checks during promotion. Revoking a materialized native record uses the existing revoke_decision lifecycle. This API does not claim automatic cross-copy revocation or discover remote reviewer state.

Legacy reports lacking explicit portable identity are rejected. Do not synthesize that missing authorization. There is no active CLI, automatic provider dispatch, implicit promotion or live policy migration in this patch. Scanner receipt formats and native currentness remain unchanged.

## Qualified provider owner

On the existing supported Windows/GitHub profile, `receiver_transport.prepare_portable_batch(gate, repository, remote, decision, received_digest)` performs read-only preparation. It pins effective Git configuration and approved Git/gh executables, derives the push endpoint from the selected repository under those pins, resolves that endpoint through authenticated GitHub API, and checks its returned immutable ID and exact route. It uses the existing gate source closure and native repository capture, then calls the materializer and ordinary promotion preview. Native identity, configuration and source closure are rechecked before returning. Unsupported routes and legacy native-only decisions fail closed. The response is a preview, not permission to publish or evidence of transfer completion.

Provider identity authenticates the repository, not the reviewer decision. The admitted caller still supplies the genuinely accepted portable decision digest. Applying the preview remains the existing separately authorized policy operation; a preview must not bypass preimage/currentness checks.

An opt-in, network-read-only synthetic regression is available as `python tests/manual_portable_owner_probe.py --expected-repository-id <provider-issued-id>`. It checks the checkout's origin, one preview and wrong-project/content-drift/legacy negatives. It does not run under automatic test discovery, run a model, publish, or write trusted policy. A real local Windows run passed all four cases; ordinary offline tests cover 1000 occurrences, duplicate/replay/revocation and existing atomic promotion.

The portable envelope additionally requires `scope: native-repository-content`. This explicitly authorizes materializing an exact content classification into the selected native repository's existing policy semantics. The provider ID is an identity admission at preparation time, not a perpetual destination restriction: existing records do not bind remote endpoints. A decision restricted to one publication destination must not be adapted through this API; it is rejected rather than broadened. Publication permission remains a separate check.
