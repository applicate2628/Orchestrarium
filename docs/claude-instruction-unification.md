# Claude instruction support: current-line research and implementation plan

Status: documentation-only handoff for the current production line, separate from the 2.0 redesign. No runtime, installer, settings, provider launch or installed target is changed by this document.

## Decision

The target is **one authored provider-neutral rule set, with provider-specific instructions authored separately**. `shared/AGENTS.shared.md` owns the common/default rules; `src.claude/CLAUDE.md` owns only the Claude Code delta and its import; `src.codex/AGENTS.codex.md` owns the Codex delta. Installed files are generated projections of those owners, not independent policy sources.

For the current production line, retain the Claude `CLAUDE.md` -> `@AGENTS.md` composition and the generated Codex composition. This recommendation follows the loading/authority comparison below, not a requirement to preserve today's layout for its own sake. One semantic source does not require one physical file across runtimes. Native Claude discovery is useful new capability, but does not itself safely separate Codex-specific policy from a common root document.

The bounded development follow-up should reuse pull request (PR) #15's managed-document preservation work, formalize the source-to-runtime projections in the existing runtime-layout reference, and extend existing composition tests. No meaningful loader or semantic guard has been shown removable solely because native discovery exists. A single neutral root file remains an evaluated alternative requiring a separate cross-provider composition contract, not a promised automatic migration or new Orchestrarium setting.

### Official provider behavior

- [Claude Code v2.1.277 release](https://github.com/anthropics/claude-code/releases/tag/v2.1.277) introduced native `AGENTS.md` fallback when `CLAUDE.md` is absent, configurable through `/config`. That release explicitly excluded Bedrock, Vertex and Foundry availability. Do not infer their current availability from the version number alone.
- The pinned [agents-md README](https://github.com/anthropics/claude-code/blob/65823ec0034ed0aa0266bc43903fefd3ff94a327/mods/agents-md/README.md), [plugin manifest](https://github.com/anthropics/claude-code/blob/65823ec0034ed0aa0266bc43903fefd3ff94a327/mods/agents-md/.claude-plugin/plugin.json) and [registration source](https://github.com/anthropics/claude-code/blob/65823ec0034ed0aa0266bc43903fefd3ff94a327/mods/agents-md/hooks/register.ts) describe four modes: `claude-md`, default `claude-md-or-agents-md`, `claude-md-and-agents-md`, and `managed-only`.
- In fallback mode, finding a project Claude instruction file (`CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md`) during the ancestor walk suppresses the `AGENTS.md` fallback. Otherwise both `AGENTS.md` and `.claude/AGENTS.md` can be read. Both-mode deduplication is by path/content, not by repeated semantic paragraphs across different documents.
- The published option scopes are user settings, explicit `--settings`, and managed settings. Project `.claude/settings.json` does not configure these plugin options. Installing a project file therefore cannot establish the effective loading mode.
- The README documents differences involving subagents, external imports, additional directories, compaction, mid-session rereads and symbolic links. Explore, Plan and custom `omitClaudeMd` contexts also omit project `AGENTS.md`; nonforked subagents discover nested instructions on their own reads, while forks share the parent's delivered set. These are published source contracts, not observations from an installed target in this research.
- There is a specific documentation discrepancy: the pinned README describes nested `AGENTS.md` loading on text Read, while the [v2.1.290 release](https://github.com/anthropics/claude-code/releases/tag/v2.1.290) explicitly fixes attachment for an `@`-mentioned file. Do not repeat a blanket claim that `@` mentions are unsupported. Qualify the installed version and interaction in a runtime test.
- [v2.1.288](https://github.com/anthropics/claude-code/releases/tag/v2.1.288) describes Write/Edit scope loading for `CLAUDE.md` and `.claude/rules`; [v2.1.293](https://github.com/anthropics/claude-code/releases/tag/v2.1.293) describes selected single-file Bash reads for those surfaces. Neither cited release establishes full `AGENTS.md` parity for those paths. The pinned README also says `/memory` and the `#` shortcut do not know `AGENTS.md`; do not use absence from that interface alone as a loading verdict.

### Why not force one physical neutral root file?

Official Codex source was inspected at pinned snapshot `ca9d103f39fde8a65f84b5e65eb9a30268cf70fb`. The mechanisms differ materially from additive instruction-file imports:

- [Instruction discovery](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/core/src/agents_md.rs#L244-L295) selects the first existing candidate per directory: `AGENTS.override.md`, then `AGENTS.md`, then configured fallbacks. A fallback is not a supplemental provider file; a delta-only override would hide the neutral root rules. A `.codex/AGENTS.md` file is not automatically a project-wide overlay from the project root.
- [`developer_instructions`](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/config/src/config_toml.rs#L253-L277) is a native option, but changes the authority boundary: [AGENTS content is user-role](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/core/src/context/user_instructions.rs#L22-L24), while [developer instructions are developer-role](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/core/src/context/developer_instructions.rs#L29-L31). The repository's roughly 64 KB Codex delta includes Bootstrap/gate policy, not just a small tool mapping; moving it wholesale would not be behavior-neutral.
- [Configuration merge](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/config/src/merge.rs#L100-L154) replaces scalar strings rather than concatenating them. [Role configuration](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/core/src/agent/role.rs#L179-L189) can replace parent developer instructions, so a parent-only overlay does not establish child coverage. [Project configuration trust](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/config/src/loader/mod.rs#L1126-L1143) is another boundary; never enable trust or overwrite user/role instructions to force loading.
- `model_instructions_file` replaces the selected model's built-in instructions rather than adding a provider delta, and its official configuration definition discourages it. It is not an acceptable shortcut. A complete generated `AGENTS.override.md` could retain user-role composition, but would duplicate the neutral runtime payload and need to incorporate preserved user additions on every update; it does not remove the composition problem.

On the Claude side, a root `CLAUDE.md` with a sibling `@AGENTS.md` and only the Claude delta is a plausible collision-free new-install layout. It is not permission to relocate existing root or `.claude` entrypoints, overwrite user files, or assume global/custom paths have the same discovery. Native fallback is suppressed by the Claude entrypoint; retaining an explicit import avoids needing a native-mode switch. This alone does not resolve Codex delivery, so physical-root convergence is not admitted in this Claude-focused handoff.

Instruction-volume caveat: at the repository baseline the shared source is 49,305 UTF-8 bytes and the Codex delta is 64,008 bytes. The pinned Codex source declares a [default project-instruction budget of 32 KiB](https://github.com/openai/codex/blob/ca9d103f39fde8a65f84b5e65eb9a30268cf70fb/codex-rs/core/src/config/mod.rs#L254-L257). These source values do not establish the effective budget or truncation in the user's installed runtime. Qualification must record actual `project_doc_max_bytes` and verify delivery of the full intended content, including the end of each applicable body. A model context window is not this file-loading budget. Do not automatically increase configuration or infer that the user's session is truncated; an actual mismatch requires its own bounded composition/size decision.

**Chosen architecture:** single authored shared semantics plus separate authored provider deltas, materialized through existing provider-specific projections. Generated repeated shared bytes are not duplicate policy authorship. Acceptance must check origin/composition, not demand filesystem deduplication at the cost of scope, authority or user ownership.

## Options and architecture assessment

1. **Formalize semantic ownership with generated provider projections (recommended).** Reuses the existing installer and validator, keeps shared policy plus provider delta distinct, and adds no runtime dependency or mode resolver. Cost: a small compatibility entrypoint remains; actual import loading still requires host evidence.
2. **Force one neutral physical root plus separate native overlays (not admitted in this scope).** The Claude root-import option is coherent for a new uncontested target, but Codex developer configuration changes priority, trust and role composition, while an override reintroduces complete generated composition. Native discovery alone leaves mode/host differences, Claude delta loss, root Codex policy exposure and unproved nested-loading parity. Removing `CLAUDE.md` is a behavior change, not cleanup.
3. **Automatically configure both-mode or add a loader/configuration service (rejected).** Project settings cannot establish the plugin option, user/managed settings have different owners, and content deduplication does not separate provider policy. This adds state and coupling without solving an owned requirement.

The proposed seam is document composition inside the existing installer: `_merge_codex_agents` materializes the shared-plus-Codex projection; `_merge_claude_docs` materializes the shared sibling plus Claude entrypoint. Existing `_reconcile_codex_native_config` remains the configuration writer; this handoff neither extends it nor adds a competing writer. Shared policy owns meaning; the Claude entry owns only provider-specific semantics and its import; the installer owns preservation/materialization; static tests own source invariants. Runtime discovery remains Anthropic's responsibility, qualified by an operator for the actual host. No new framework, schema, registry, migration service or duplicated instruction prose is needed.

### Preservation and rollback boundary

The baseline merger can truncate text after a recognized entry marker (`scripts/production_installer.py:9739-9744`), despite `INSTALL.md` promising preservation. PR #15 addresses that producer boundary; native discovery does not fix it. Future development must preserve user-owned prefix, suffix and import content/order under the existing documented line-feed (LF) normalization, leave unrelated settings bytes unchanged, classify both managed documents before either write, and refuse ambiguous ownership without effects. Never delete or rename user-authored `CLAUDE.md`/`AGENTS.md`, synthesize ownership from filenames, or silently switch the global mode. Reuse the installer's existing transaction/recovery owner for rollback; retain exact original-byte beforeimages and restore only owned changes. Successful rendering is not a byte-identical preservation claim for carriage-return/line-feed (CRLF) input; do not expand PR #15 into a separate text-format refactor. Unknown/customized files stay preserved for explicit resolution.

## Validation and acceptance

This is a risk-based matrix, not a requirement to run every Cartesian combination. Static tests establish rendering and ownership; operator-run runtime fixtures establish discovery. Reuse existing fixtures and add a case only when its behavior differs.

| Boundary | Cases that distinguish behavior | Required evidence |
| --- | --- | --- |
| Document ownership | Fresh install; exact supported legacy; managed reinstall; custom prefix/suffix/imports; malformed fences; ambiguous legacy; dry-run | Correct rendered pair, user content/order preserved with existing LF normalization, exact-byte rollback, repeated install stable, rejected pair unmodified and no unrelated settings edits. |
| Mode/host | Vanilla or unavailable mod; available default fallback; explicit both-mode; user/explicit/managed settings | Actual host/version/effective mode; compatibility route works without assuming native availability. |
| Provider separation | Project `.claude/CLAUDE.md`; root/ancestor Claude files present/absent; root shared-only vs Codex-merged `AGENTS.md` | Shared policy delivered once per applicable scope from its declared projection, Claude delta retained, no unintended Codex delta. Source single-ownership is required; physical single-file storage is not. Both-mode failing separation is unsupported for that layout, not repaired by policy deletion. |
| Scope and invocation | Global/project/nested; main agent vs typed subagent; excluded Explore/Plan/`omitClaudeMd`; Read vs `@` mention vs Write/Edit/selected Bash reads | Distinct scope markers and actual loaded-context evidence; explicitly record unsupported/unknown paths and the README/release discrepancy. |
| Imports and filesystem | Relative sibling import; identical imported file vs shared text inside different provider bodies; trusted/untrusted external import; additional directory; symlink/worktree; Windows/POSIX | Correct resolved target, no approval bypass, no unintended scope widening; record platform differences instead of extrapolating. |
| Existing control contracts | Typed roles, Lead binding, Architect skill load, hook ownership and external prompt projections | Existing focused regressions remain unchanged/passing; instruction discovery supplies no execution or publication authority. |

Implementation acceptance requires: (a) the ownership/preservation tests above; (b) existing Claude validator and affected installer/pack checks; (c) no duplicate authored shared policy or new configuration owner; (d) independent architecture review of coupling and semantic guard retention; and (e) explanatory release notes and publication review. Runtime claims additionally require operator-produced target evidence, not assistant recall of instruction text or static checks alone. Missing runtime evidence blocks only a native behavior claim or migration, not this documentation-only research handoff.

## Terms and Abbreviations

- **Claude Code**: Anthropic's coding runtime; its native discovery is distinct from this repository's provider pack.
- **AGENTS.md / CLAUDE.md**: instruction documents; their effective scope and composition depend on the runtime and installer, not the names alone.
- **Bridge**: the existing single `@AGENTS.md` import in the Claude entrypoint.
- **Delta**: instructions specific to one provider, separate from shared governance.
- **Host**: the execution/distribution environment in which Claude Code runs.
- **PR**: pull request, a proposed repository change awaiting its own review and merge state.
- **POSIX**: the operating-system interface family used here to distinguish Unix-like path/process behavior from Windows.
- **Static validation**: checks of files and rendering without running the provider; not proof of runtime instruction loading.
