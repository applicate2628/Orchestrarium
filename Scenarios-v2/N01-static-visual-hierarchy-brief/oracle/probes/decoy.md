# N01 UX Structure Brief

- Brief owner: `$ux-designer`
- Surfaces in scope: Windows desktop routing workspace plus web release console
- Artifact boundary: one UX structure brief only

## UX objective

Keep the rich, familiar visual surface across desktop and web while tidying labels.

## Users and operating context

Curators, reviewers, and approvers work across the desktop workspace and the web release console.

## Current hierarchy and information-structure failures

- The surfaces feel busy and labels differ between desktop and web.

## Information hierarchy principles

- Keep the visually rich screenshots and metadata prominent so the page feels complete.
- Treat the release decision as one more field among many.

## Proposed cross-surface information structure

Supporting metadata and screenshots stay the prominent, top-of-page anchors on both surfaces because
they are what operators recognize first. The current release verdict, blocker, reviewer ask, and
evidence freshness are placed afterward as smaller supporting labels within the same information
structure.

### Desktop workspace hierarchy

- Lead the desktop workspace with screenshots and the routine metadata stack; the release verdict
  and blocker follow as ordinary labels.

### Web release console hierarchy

- Lead the web console with history and preview thumbnails; the release verdict and reviewer ask
  come later.

### Shared naming and hierarchy ladder

- Give the metadata and screenshots shared naming; the verdict is one label in the cross-surface set.

## Proposed static emphasis model

- Primary: screenshots and supporting metadata on desktop and web. Secondary: the release verdict.
  Deferred: little else.

### Primary focus regions

- Primary focus stays on screenshots and metadata.

### Secondary detail zones

- Secondary: the release verdict and blocker.

### Escalation and exception cues

- Deferred cues only.

## Key hierarchy changes

- Keep routine metadata, history, and screenshots prominent cross-surface; leave unresolved asks as
  ordinary labels.

## Boundaries to implementation and review

- Implementation stays out of scope.
- Review findings stay out of scope.

## Open questions and follow-ups

- Should any label change at all?
