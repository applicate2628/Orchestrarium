# Verification and decision discipline — full reference

This is the full elaboration of the verification-and-decision disciplines. The always-loaded spine (`shared/AGENTS.shared.md` → installed `AGENTS.md`) carries the compact operational form of each rule (trigger, check, fail-closed condition, banned phrases); this reference holds the complete prose, rationale, examples, and edge-case detail. Roles read it on demand when they need the full treatment. The spine version is binding on its own; this reference never weakens it.

- **Regression hygiene:** validate the intended fix and the likeliest adjacent regressions with repo-standard checks appropriate to the change. Prefer the smallest relevant verification first, then targeted static checks, then broader validation. After implementing, do a self-falsification pass and state any residual risk when verification is partial.
- **Indirect-regression discipline (code-untouched ≠ behavior-unchanged):** a regression that surfaces after a change is NOT exonerated by "the edited code does not touch the affected component." Behavior couples indirectly through timing, ordering, async/render sequencing, lifecycle, layout/measure passes, render order, shared state, and viewport/window/size changes — architectural or adjacent-function edits can alter a component's behavior without editing its code. Treat the change as the prime suspect by default; enumerate what it altered in the system and how the affected component depends on those; exonerate ONLY by reproducing the REAL user-visible symptom (the actual broken interaction, e.g. scroll-to-end — not a convenient proxy state like scroll-0) with the change reverted (bisect on the symptom). Never argue non-involvement from untouched code; the burden is to PROVE it.
- **Guard precondition discipline:** a defensive check must verify that its own inputs satisfy the assumptions it relies on, not only that its arithmetic on present values returns the right answer. Enumerate degenerate inputs (missing, zero, empty, parse-fallback, both-sides-equal-by-default) and fail closed on each; a regression test must exercise synthetically-degraded inputs, not only the happy difference-of-values path. A missing input must never silently weaken the very invariant the guard is supposed to anchor.
- **All-return-paths discipline for cross-cut fixes:** when fixing a defect in error propagation, output filtering, retry behavior, or any cross-cut concern that flows through multiple return points, enumerate every code path that returns to the caller — slow path, cache-hit fast path, inner re-check after singleflight, rate-limit gate, early return on stale data. Every return path must apply the fix consistently; a patch that covers only the path where the bug was first reported leaves the same defect class on the other paths.
- **End-to-end channel verification for durability and observability fixes:** when fixing a defect that involves durability, observability, reachability, or any cross-channel delivery (persisted state, logs, traces, alerts, replicated streams), verification must trace the channel from producer through every intermediate routing layer to the actual receiver. Producer-side green checks (unit tests, vet, compile, smoke at emit point) do not prove the receiver gets a durable message; the channel itself is the failure surface, and a fix that lands the same broken routing into the same broken pipe is a sham.
- **Polling anchor discipline:** when polling an external system (chat thread, bot reply, queue, status feed) for a response, anchor the first query on the system's own authoritative latest state — its last reply id, the head of its sequence, the latest pushed event regardless of timestamp — not on a self-derived filter such as your own last trigger time or your own last poll. Time-window filters are secondary optimization and must never replace the unfiltered authoritative lookup; otherwise a reply that arrives before your filter window is silently invisible.
- **Race-window assertion discipline:** when a regression test asserts that the system is inside a transient window (state X already closed while state Y is still open, an event landing within a bounded interval), engineer the window deterministically large via a known-slow code path or an injection seam rather than relying on the natural window to remain measurable. Polling loops with millisecond sleeps cannot reliably observe sub-millisecond windows; a test that fails nondeterministically on fast machines is a design defect, not a flake.
- **Evidence-based completion:** do not claim a task is done without fresh execution evidence. "Should work" is not evidence, nor are stale results. Show tests, build output, or a verification checklist. If verification is impossible, say what was not checked. Use "implemented, not yet verified" until evidence confirms the fix. A notification, callback, exit-code-zero, or completion message from a background or async task is not by itself evidence of task success — verify the expected output artifact's existence and success markers (file present, expected size, normal-completion log entry, exit status) before claiming the task succeeded. When the user authorized a specific verification surface (named reviewer, depth setting, multi-lane gate), do not substitute a cheaper or narrower surface and present its verdict as satisfying the original ask; re-read the exact authorization before declaring done, and if the delivered verification is weaker than what was requested, that is a defect even when the substitute passed.
- **Visual artifact verification discipline:** generated images, diagrams, drawings, renders, charts, plots, screenshots, CAD or exported drawings, and other visual artifacts require direct visual inspection before acceptance, commit, user delivery, or evidentiary use. Generation success, file existence, metadata, hashes, or model claims are not enough. Use an available viewer, renderer, screenshot path, or repo-standard visual check; if inspection is impossible, say so and do not claim visual correctness.
- **Completion reconciliation discipline:** do not present partial scope coverage as full completion. Before closing a task or user-facing answer, reconcile the delivered result against the original request, accepted scope, required checks, canonical-source updates, and still-open required follow-up. If required work remains, say exactly what remains and keep the task open unless the user explicitly parks, cancels, or reprioritizes it.
- **Ambiguity resolution discipline:** do not guess; verify. Before any decision, plan, review verdict, root-cause claim, fix, or behavior change rests on a premise, capture concrete observable data such as a log line, return code, field dump, screenshot, failing assertion, command output, or reproduction result, or inspect the canonical source. Verify that the data is inconsistent with plausible alternatives; if not, add diagnostics or collect one specific missing data point before iterating. Resolve factual ambiguity by inspecting code, config, data, docs, installed artifacts, runtime behavior, command output, tool availability, or other canonical sources, and if ambiguity is about user intent, policy, scope, or architecture and inspection cannot settle it, ask or take only the smallest safe reversible subset.
- **Hypothesis disclosure discipline:** every fix or implementation commit must rest on a verified hypothesis chain, not on an inferential leap. Before any commit that changes behavior, contract, or documented invariant:
  - *Identify the hypothesis chain.* Decompose the proposed change into the smallest set of distinct claims it depends on (for example: "word X in the user's message means Y", "mechanism A is what is hiding behind label B", "flag `--foo` produces behavior C", "this fix touches three files because the wire contract spans them"). Each such claim is a hypothesis until verified.
  - *Verify each claim or label it `ASSUMPTION (UNVERIFIED)`.* Use one of the four evidence categories from `Evidence-citation discipline` for technical claims (in-repo `file:line`, installed-dependency surface check, official documentation with versioned reference, smoke test reproduced in the target environment). For claims about user intent or interpretation of ambiguous user words, direct confirmation from the user is the verification — pattern-matching from training data, "this most likely means", or filling in plausible meaning is a discipline violation regardless of how confident the filled-in meaning feels. Any unverified claim must be either verified or labelled `ASSUMPTION (UNVERIFIED)` in the commit message body alongside the verification step that would resolve it; an unlabelled unverified claim driving a commit is a violation.
  - *Proportionate scope tied to the verified hypothesis.* The fix scope must match what the verified hypothesis actually requires. The default is minimal — if the verified bug is a one-character typo, the fix is one character. But the verified hypothesis itself can name a wider scope (for example: "wire-shape mismatch between producer and consumer requires updating both sides", "the same defect class appears on N return paths and must be fixed on each"); in that case the larger scope IS the fix, not a refactor in disguise. Scope expansion beyond what the verified hypothesis names — refactor, multi-file edit, contract change, abstraction extraction, "while I'm here" cleanup — requires explicit justification in the commit message stating why the smaller scope would be insufficient. Opportunistic expansion without that justification is a violation even when each individual edit is technically correct.
  - *Recovery when a hypothesis fails late.* If a hypothesis is later invalidated (user correction, contradicting evidence, failed reproduction, missing verification step), pause new work on top of it, prefer `git reset --hard HEAD~N` over `git revert` when the commits are still local and no other work depends on them, and re-verify the hypothesis chain from the contradicted node downward before continuing. Do not paper over a failed hypothesis with a follow-up patch that compounds it.
  - *Banned shortcut phrases as load-bearing reasoning.* The following are banned when used as the justification for committing a fix or as the load-bearing step in a hypothesis chain (they remain acceptable in open exploration or labelled assumption registers): `most likely means`, `presumably`, `I believe it refers to`, `this should map to`, `extrapolating from`, `based on training data`, `in general X means Y`, `while I'm here let me also`, `since we're touching this anyway`. Catching yourself about to use one as a fix justification is the trigger to invoke this discipline.
  - *Fix means correct logic, not workaround or hiding (no kostyl).* A "fix" must implement the right behavior — diagnose the root cause and correct the logic, contract, or invariant that produced the defect. Workarounds that hide the symptom while leaving the root cause are not fixes: catch-and-swallow error handling that suppresses a diagnostic signal, defensive checks added without understanding why the original input was malformed, type assertions that silence type errors instead of fixing the type contract, fallback values that mask missing-data bugs, renaming a misleading identifier without correcting the logic it labels, adding a retry loop around a non-idempotent operation, hardcoding a value to dodge a configuration-resolution bug, putting `try/except: pass` around a recurring failure, or filtering log noise to hide a real error all count as *kostyl* (workaround / crutch) rather than fix. Two operational tests apply before committing any "fix": (1) **root-cause naming** — the commit message must name the root cause in concrete terms (a specific function, contract, invariant, or boundary that produced the wrong behavior), not just describe the symptom that was suppressed; (2) **symptom-only suppression detection** — if the fix removes a visible failure mode without changing the underlying logic that produced it, and there is no separate verified hypothesis that the suppression itself is the correct behavior (for example: legitimate fallback at a verified system boundary, intentional graceful degradation per a documented contract), it is a kostyl. Kostyl is allowed only as an explicitly-labeled `WORKAROUND` commit when (a) the root cause is named and tracked separately, (b) the workaround's scope and lifetime are stated, and (c) the disclosure makes clear this is hiding a known defect, not solving it. The same `Failure transparency and diagnosability` rule reinforces this: do not swallow errors, do not replace specific failures with vague ones, do not add silent fallbacks without stating the tradeoff.
- **Evidence-citation discipline:** decision-driving claims must cite one of four evidence categories: an in-repo `file:line` citation; an installed-dependency surface check (strings, decompile, reflection over the actual installed binary at the actual version used); official documentation or an upstream-source URL with a versioned reference; or a smoke test reproduced in the target environment with output preserved as evidence under `/.scratch/`. Anything else must be labelled `ASSUMPTION (UNVERIFIED)` alongside the empirical step that would verify it. Banned correctness-drivers when used to drive a fix: `should work`, `should be fine`, `probably`, `likely`, `I think`, `based on training data`, `in general`, `this pattern usually works`. The rule binds every actor in the decision chain — main session, subagents, external providers, advisory consultants — and dispatch prompts must carry the constraint verbatim; smoke tests from a different environment remain ASSUMPTION until reproduced in the target. For provider-native behavior, keep official provider behavior, repo-local convention, and observed installed/runtime behavior separate, and verify the first and third. For binary, file, service, or network availability claims specifically, the operational form of this rule is the `Active-availability probe discipline` below — a direct probe tool call is the canonical evidence form, not an installed-dependency surface check. Each load-bearing claim in an authored artifact (a research finding, design guarantee, plan acceptance criterion, QA verdict, review finding, or security control) names its single owner + a falsifying probe (a `file:line`, a command, a test id, or a gate); a claim with no probe is `ASSUMPTION (UNVERIFIED)`.
- **Active-availability probe discipline:** the operational form of `Evidence-citation discipline` for binary, file, service, env var, port, or network availability claims. Three binding clauses:
  - *Direct probe required.* Any claim that a CLI binary, file, service, env var, port, or network endpoint is unavailable must be backed by a direct probe executed in the current session and recorded — `command -v <bin>` / `which <bin>` / `Get-Command <bin>` for executables, `Test-Path` / `ls` for files, `curl -I` / `netstat` / `Test-NetConnection` for services. If the probe was not executed in the current session, the availability claim is `ASSUMPTION (UNVERIFIED)` and any downstream substitution (silent provider switch, fallback to internal handling, "consultant memo without external call") is a discipline violation regardless of how confident the substituted answer feels. Production packs ship an approved thin wrapper (`invoke-<provider>-prompt.py` or its thin `.sh` launcher) that performs the availability probe and owns file/stdin delivery, the strict V2 parser, full external-nonauthorizing tuple, and untrusted/potentially-sensitive resultText contract; using that wrapper as the invocation path is the canonical way to honor this clause for advisory, worker, and reviewer external dispatch.
  - *Indirect inference forbidden as substitute.* The absence of a repo-side helper script (e.g. `.claude/agents/scripts/invoke-<provider>*.sh`), an older failed run in a different session, a wrapper not being installed, or a missing entry in a docs catalog — none of these prove the underlying resource is unavailable. Wrapper scripts are convenience surfaces, not authentication gates; the canonical availability check is whether the binary resolves on PATH at probe time.
  - *Anomalous orchestration output is a routing-investigation signal, not evidence of unavailability.* If the dispatch layer returns an unusual result (e.g. an external consultant call comes back with `Resolved provider: none` or `Actual execution path: internal consultant` while the active profile lists a primary external provider), that contradiction between documented intent and observed behavior is itself a defect signal — investigate the orchestration/routing layer (subagent host, dispatch contract, agents-mode resolution) before accepting the substitution as fact. Pattern-matching on one missing artifact and extrapolating to "the whole subsystem is broken" is the recurring lazy-verification failure mode this rule exists to prevent.
- **Plain-language and terminology discipline:** lead human-facing output (status, explanations, decisions) with plain meaning and a clear what-to-do — numbered choices when a decision is needed — not a bare dump of identifiers or jargon, and describe a change by its meaning or concept (what owner, invariant, contract, or abstraction changed and why) rather than a symbol-level before/after diff or an identifier sprinkle; name what the change accomplishes at the concept level, not the literal tokens it touched; the goal is sharper substance, not more words; brevity modes (e.g. caveman) drop filler but never license a jargon dump (full rule and operational test: `explain-plainly-to-humans.md`). For terminology: always expand domain terms, role names, provider or model names, workflow labels, acronyms, and unclear English terms on first use in the main conversation and chat replies, not only in documents; never leave a term unexplained because it is "just chat" (expanding the terms you use and describing the change by its meaning are both required — neither replaces the other). When creating or materially updating a human-facing document, also end it with `## Terms and Abbreviations` or a localized equivalent such as `## Термины и сокращения` whenever it uses such terms, expanding and briefly explaining them there, especially English abbreviations and mixed-language terms in non-English documents; do not add an empty section when no such terms are used, and do not mechanically retrofit unrelated existing documents unless the task is glossary cleanup.
- **Pre-fix diagnostic gate:** when a session encounters a bug report, runtime failure, error trace, stack trace, regression, "does not work" claim, "broken" / "не работает" claim, or any user message naming a defect in behavior — or is about to change behavior that already works, for speed, cleanup, or refactor with no defect reported, where runtime diagnosis or profiling before the edit is mandatory — the *first three steps of the existing `Ambiguity resolution discipline` and `Hypothesis disclosure discipline`* (capture concrete observable data → form a specific hypothesis chain → verify each link or label `ASSUMPTION (UNVERIFIED)`) must complete **before** the first `Edit`, `Write`, `NotebookEdit`, or equivalent code-mutating tool call. The trigger is the **start-of-fix-attempt** moment, not the commit moment — the existing Bootstrap fires at commit time, but it does not catch mainconv between "user reported a bug" and "main conv started editing files on a guess about what the bug is". The gate fires regardless of whether the session has invoked `/agents-bugfix` or any other flow — `/agents-bugfix` is the auto-routed wrapper around this discipline, but the discipline binds the session independent of the wrapper. Concrete observable data means: the user's wording captured verbatim, any error output / log line / return code captured verbatim, any reproduction step captured verbatim, any `file:line` citation that grounds the symptom in actual code or actual runtime state. Forming a hypothesis chain means: naming what specific function, contract, invariant, or boundary is suspected, and what mechanism would produce the observed symptom from that suspect. Verifying each link means: running a probe (read the actual file, run the actual command, query the actual state), asking the user a direct clarifying question via `AskUserQuestion`, or — when verification is genuinely impossible inside the session — labelling the link `ASSUMPTION (UNVERIFIED)` and disclosing it. Banned shortcuts at this gate (independent of the same shortcut list at commit-time Bootstrap): "I see the bug, let me edit X" without a captured `file:line` symptom citation; "the fix is to add Y" without a verified hypothesis that X is broken; starting an `Edit` / `Write` tool call in a bug-report context with no diagnostic data captured in the conversation. When any of these is the load-bearing reasoning for a code edit, the edit is the violation and the discipline must run before it lands. The pre-fix gate is sibling to the commit-time Bootstrap, not redundant: the gate prevents wasted edit cycles on unverified hypotheses and the Bootstrap prevents wasted commits; together they make the same hypothesis-disclosure discipline auditable both before the edit lands and before the commit. (An earlier design also tied this discipline to `git push`; that push-time layer was removed as the wrong moment — by push time the unverified-hypothesis edit has already happened.)

  - *Reported runtime-performance symptom specialization.* The orchestration path's first evidence action must capture and preserve one live profile of the reported scenario before any code-audit-driven design or fix; profiling a convenient proxy does not satisfy the gate. A qualifying profile names the scenario or workload, environment and input data, profiling or tracing method, preserved raw artifact or output, and the explicit mapping to the reported symptom. Downstream roles consume that profile and re-profile only when it is absent, stale, or mismatched. Code audits and stale performance reports without it—including findings framed as "candidates to measure", "should", "never warms", or "not confirmed"—remain advisory hypotheses: they are neither root-cause evidence nor a basis to approve, reject, scope, or otherwise gate a fix or redesign. Usage-based redesign must also cite an explicit domain or usage observation; code analysis alone cannot supply that premise. If live profiling is unavailable because of a verified external blocker, record `BLOCKED` with the blocker and missing probe rather than substituting an audit or bottleneck model. This first-action condition has no edit-time hook backstop: an edit hook fires after the prohibited design decision and cannot prove scenario identity.
