# Методология design-panel (провайдер-нейтральная)

Канонический ИСТОЧНИК ДИЗАЙНА для техники design-panel — независимой многодорожечной ГЕНЕРАЦИИ по одной закреплённой дизайн-задаче, сходящейся через один обязательный синтез. Этот справочник провайдер-нейтрален и НЕ устанавливается ни в один рантайм (согласно `shared/references/README.md`). Каждый production-пак поставляет тонкую РАНТАЙМ-привязку, которая несёт операционные правила: Claude → `agents/contracts/design-panel.md` (читается командой `/agents-design-panel`); Codex → `skills/design-panel/`. Держите этот ствол свободным от пак-специфичных деталей исполнения (никаких конкретных API диспетчеризации, путей к обёрткам или синтаксиса CLI); они живут в привязках конкретных паков.

## Назначение

Получить независимую многодорожечную **генерацию** дизайн-кандидатов по одной закреплённой задаче ДО того, как появится единый дизайн, затем свести их через один обязательный синтез в единственный артефакт, годный для планировщика. Это отличается от прочих поверхностей дизайна и ревью: это не одна дизайн-цепочка (`/agents-design`), не петля ревью (которая верифицирует уже существующий артефакт), не второе мнение (одна консультативная записка) и не бригада (разрозненные параллельные дорожки, каждая владеет своим артефактом). design-panel — это осознанная, более тяжёлая поверхность — N попыток дизайна сильной моделью по одной задаче — а не стандартный маршрут дизайна.

## Когда панель окупается (два допустимых триггера)

- **Механические зачистки с большим числом поверхностей.** Дизайн-задача содержит достаточно независимых поверхностей (файлов, контрактов, точек интеграции), что одна дорожка вряд ли перечислит их полностью; объединение независимо-обрамлённых дорожек полнее любой одной дорожки.
- **Открытые архитектурные выборы.** Дизайн-задача имеет более одной защитимой архитектуры, и выбор выигрывает от независимо исследованных альтернатив перед принятием решения.

Антитриггеры: аддитивный дизайн одного модуля, либо любой дизайн, чья постановка задачи ещё не проверена (сначала проверьте предпосылку — панель умножает непроверенную предпосылку в N раз).

## Инварианты design-panel (DP1–DP8)

Каждая установленная привязка несёт те же устойчивые ID с языком исполнения, специфичным для провайдера. ID — это якоря соответствия, а не замена операционного текста.

| ID | Требуемый инвариант |
| --- | --- |
| `DP1 — Закреплённый вход` | Lead принимает одну цель, допущенную область, пакет свидетельств/ограничений, ожидаемый финальный артефакт и владельца синтеза ДО диспетчеризации. Все кандидаты получают идентичный базовый пакет; различается только заявленная надстройка-обрамление (framing). |
| `DP2 — Кворум` | Требуется минимум два валидных, дизайн-способных кандидатских артефакта. По умолчанию `N=2`; дополнительные дорожки требуют отдельного обрамления и обоснованной стоимости слияния. Слабая, провалившаяся, пустая или дублирующая обрамление дорожка не засчитывается. |
| `DP3 — Независимость` | Независимость происходит из разной области/обрамления и изолированных свежих контекстов, а не из числа вендоров. Кандидаты не видят промпты, выходы, находки или статус друг друга до возврата. Разные вендоры с одинаковым обрамлением не являются независимыми; один и тот же способный движок в свежих контекстах с подлинно разными обрамлениями — может быть. |
| `DP4 — Кандидат — только вход` | Каждый кандидат несёт `Panel disposition: INPUT_ONLY`, называет свою дорожку/обрамление и идентичность закреплённого входа, и возвращается владельцу синтеза. Он не может быть назван каноническим `design.md`, зафиксирован как последний принятый дизайн, передан `$planner` или выдать `PASS` дизайн-стадии. |
| `DP5 — Обязательное сравнение` | Заранее объявленный владелец синтеза получает **ВСЕ** валидные кандидаты и производит явную матрицу сравнения: согласие, уникальные вклады дорожек, конфликты, упущения и диспозицию с свидетельством/обоснованием. Панели механических зачисток берут проверенное объединение совместимого покрытия; панели архитектурного выбора выбирают или связно комбинируют варианты, а не голосуют большинством и не объединяют вслепую несовместимые дизайны. |
| `DP6 — Единственный гейт продвижения` | Только артефакт синтеза может нести Change-Surface Contract архитектора, финальные пронумерованные claims, устойчивые идентификаторы решений и `PASS` на следующую стадию. Вызов панели возвращает ровно один публичный результат: синтез либо неуспешный статус. |
| `DP7 — Отказ закрытием` | Пропавшие/упавшие/пустые дорожки — `UNVERIFIED`; дублирующие обрамления обнуляют кворум; неразрешённые конфликты возвращают `REVISE`; менее двух валидных кандидатов возвращают `BLOCKED:dependency`. Молчание никогда не является чистым вкладом. |
| `DP8 — Один заход, затем верификация` | Генерация кандидатов происходит один раз; синтез — это шаг сходимости. Нет счётчика раундов, цикла повторной диспетчеризации или пораундового леджера антидрейфа. Если синтезированный дизайн нуждается в независимой верификации, передайте этот один артефакт в review-loop или в обычную цепочку дизайн-ревью. |

## Поток артефактов: от кандидата к синтезу

```text
одна закреплённая дизайн-задача
            |
            v
   N >= 2 изолированных кандидатских дорожки (свежие контексты, разные обрамления)
   каждая возвращает Panel disposition: INPUT_ONLY
            |
            v
   один обязательный синтез (сравнение + матрица диспозиции)
            |
            v
   единственный артефакт дизайна, годный для планировщика
```

Кандидат — это полное, готовое к сравнению дизайн-предложение — это не набросок. Он просто не годен для самостоятельного продвижения дизайн-стадии. Только шаг синтеза производит канонический артефакт дизайна и несёт `PASS` дизайн-стадии.

## Правила сравнения (сравнение на уровне МНОЖЕСТВ, никогда не голосование большинством)

Владелец синтеза сравнивает кандидатов на уровне их claims и поверхностей, а не на уровне счётчиков согласия — если две дорожки нашли «40 пунктов», это ничего не доказывает, если множества не пересекаются.

- **Панели зачистки поверхностей** берут **проверенное объединение** совместимого покрытия: каждая уникальная для дорожки находка проверяется по существу и либо включается, либо отклоняется с названной причиной. Совпадающие счётчики — не доказательство полноты.
- **Панели архитектурного выбора выбирают или связно комбинируют** варианты, а не голосуют большинством и не объединяют вслепую несовместимые дизайны — две несовместимые архитектуры не могут быть приняты по частям одновременно.
- **Никогда не голосование большинством.** Диспозиция решается проверкой claim каждого кандидата против свидетельств и принятых ограничений, а не подсчётом того, сколько дорожек его предложили.

## Отношение к review-loop

design-panel и review-loop разделяют один принцип независимости — один и тот же движок в двух различных обрамлениях — это две независимые дорожки; само по себе число вендоров не есть независимость (см. `review-loop-methodology.md#the-angles-two-smart-verdicts--one-mechanical-scout`) — применённый на разных стадиях. design-panel — это независимость на **генерации**: он производит N кандидатских дизайнов до того, как появится хоть один артефакт. review-loop — это независимость на **верификации**: он сводит несколько углов по одному уже написанному артефакту через раунды. Композиция последовательна, а не конкурентна: панель генерирует и синтезирует один раз → `design.md` → опциональный review-loop верифицирует этот один артефакт до сходимости → планировщик. design-panel не переизлагает таксономию углов, предел раундов или леджер состояния review-loop.

## Граница валидатор/ревью

Механические проверки (существование файлов, наличие ID-инвариантов и маркеров, наличие путей установки) принадлежат валидаторам паков. Являются ли два обрамления подлинно независимыми, а не переименованными дубликатами, нашёл ли синтез каждый уникальный вклад, и годен ли финальный дизайн к отгрузке — всё это остаётся территорией ревью: структура механически проверяема, здравость — нет.

## Термины и сокращения

- **кандидат (candidate)**: выход одной независимо-обрамлённой дизайн-дорожки; достаточно полон для сравнения, но не годен для самостоятельного продвижения (`Panel disposition: INPUT_ONLY`).
- **обрамление (framing)**: отдельная область, угол или декомпозиция задачи, назначенная одной дорожке; источник независимости, а не вендор.
- **свежий контекст (fresh context)**: контекст исполнения, который не видел промпт или выход дорожки-соседа.
- **кворум панели (panel quorum)**: минимум два валидных, дизайн-способных, независимо-обрамлённых кандидатских артефакта (`N >= 2`).
- **синтез (synthesis)**: обязательный шаг сравнения/слияния, производящий единственный артефакт, годный для планировщика.
- **`INPUT_ONLY`**: диспозиция кандидата, означающая, что артефакт может питать синтез, но не может самостоятельно продвинуть дизайн-стадию.
- **`RETURN(lead)`**: форма гейта леджера, используемая для возврата завершённого прогона кандидата владельцу синтеза без объявления `PASS` дизайн-стадии.
- **review-loop**: отдельный многораундовый процесс, верифицирующий один существующий дизайн до сходимости.
- **PASS / REVISE / BLOCKED**: вердикты гейта — принять, вернуть на ограниченную правку или остановиться на реальном внешнем блокере.
