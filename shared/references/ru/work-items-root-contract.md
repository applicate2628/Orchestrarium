# Корневой контракт work-items

Это канонический общий контракт для расширения топологии Physical Lifecycle V1
по пути `work-items/root-contract.json`. Единственный владелец разрешения этого
контракта для операций жизненного цикла — `ProjectTopology`. Physical Lifecycle
V1 — версия модели жизненного цикла; версия дисковой схемы root-contract ниже —
2. Семантическое принятие принадлежит английскому оригиналу.

## Точная схема

Контракт необязателен. Если он есть, это обычный UTF-8 файл JavaScript Object
Notation (JSON) по относительному к репозиторию пути
`work-items/root-contract.json` и ровно с этими ключами, без дополнительных:

```json
{
  "schema": "work-items-root-contract",
  "version": 2,
  "auxiliaryRoots": {
    "repair-receipts": { "kind": "flat-json" }
  }
}
```

`auxiliaryRoots` — объект: его ключи являются именами вспомогательных
каталогов, а каждое значение строго равно `{ "kind": "flat-json" }`. Имя
должно быть одним простым slug, относительным к репозиторию: оно не может быть
абсолютным, содержать разделитель пути или обход `..`, либо называть
зарезервированный встроенный корень жизненного цикла. Встроенные корни остаются
владением `ProjectTopology`, включая `backlog`, `active`, `archive` и текущие
корни встроенных плоских категорий; их НЕЛЬЗЯ повторно объявлять в
`auxiliaryRoots`.

Генерируемый файл верхнего уровня `work-items/README.md` также
зарезервирован. Имя вспомогательного корня НЕ ДОЛЖНО совпадать с `README.md`
при регистронезависимом сравнении. Это правило не зависит от хост-системы,
поэтому контракт, принятый в регистрозависимой файловой системе, не сможет
создать псевдоним генерируемого файла в регистронезависимой файловой системе.

Каждый объявленный вспомогательный корень ограничен путём
`work-items/<name>`. Он может отсутствовать, но при наличии обязан быть
каталогом. Корень репозитория, `work-items/`, файл контракта и каждый
объявленный корень должны быть путями без reparse point и без ссылки. Объявление
не разрешает другое место в репозитории или вложенную иерархию категорий.

## Поведение жизненного цикла

`ProjectTopology` передаёт один и тот же набор разрешённых корней в audit,
close, reopen и обновление генерируемого `work-items/README.md`. Объявленный
корень `flat-json` — проектный вспомогательный каталог верхнего уровня, поэтому
audit не считает его неизвестным; в остальном он не входит во встроенный
жизненный цикл элемента. Close и reopen перемещают только записи work-item, а
README остаётся производным представлением, а не источником топологии.

При отсутствии контракта для совместимости сохраняется прежнее поведение только
со встроенными корнями. Если контракт повреждён, имеет неизвестную схему или
версию, объявляет небезопасный, зарезервированный, ссылочный, reparse,
нелокальный или не-каталоговый корень, операции жизненного цикла закрываются с
ошибкой `WI-CATEGORY-ROOT-CONTRACT-INVALID`. Они не выполняют зависящее от
топологии перемещение или обновление README. Исправьте контракт и повторите ту
же команду жизненного цикла; архивные идентичности неизменяемы, поэтому
восстановление не возвращает уже архивированный элемент, а использует обычный
явный путь successor/reopen.

## Термины и сокращения

- `auxiliary root`: объявленный проектный каталог верхнего уровня `work-items/`
  с видом `flat-json`.
- `flat-json`: единственный вид вспомогательного корня Version 2; резервирует
  один плоский каталог верхнего уровня, не создавая категорию жизненного цикла.
- `JSON`: JavaScript Object Notation, формат файла контракта.
- `ProjectTopology`: владелец жизненного цикла, разрешающий встроенные и
  объявленные вспомогательные корни work-items.
- `reparse point`: перенаправление файловой системы, например символическая
  ссылка или платформенный reparse-объект; такие пути контракт отклоняет.
