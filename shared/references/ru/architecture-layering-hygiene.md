# Гигиена слоистой архитектуры — обобщённые best-practice

Источник-истины для мейнтейнера (читается по требованию; НЕ устанавливается в таргеты). Компактная,
проверяемая форма едет в определениях ролей `$architect` и `$architecture-reviewer`, которые ссылаются
на этот файл. Обобщённо — независимо от провайдера / домена / языка; законы сформулированы как
проверяемые тесты, не лозунги, и каждый называет ВЛАДЕЛЬЦА, которого защищает, плюс ПРОВЕРКУ-ЗОНД,
ловящую нарушение. Синтезировано из правила layer-library одного численного солвера и очищено от его
доменной специфики (FEM/MoM, CMake, strict-FP byte-gate); остался только обобщаемый сердечник. Законы
задают УМОЛЧАНИЯ с именованными исключениями — применять как pressure-тесты, не абсолюты (абсолютное
прочтение порождает ложные findings).

## Принцип

Дели систему на МОДУЛИ по СЛОЮ ответственности, каждый — единица одного владельца с узким интерфейсом,
и КОМПОНУЙ их — НЕ в большие независимые программы-на-фичу, каждая со своими приватными копиями общих
слоёв («силос»). Фича / вариант / сценарий — это ТОНКАЯ СБОРКА над общими слоями, никогда не форк их.
Применимо ко ВСЕМ уровням абстракции: каждый слой сам единица одного владельца, чьи потребители (включая
верхние слои и фича-скрипты) остаются тонкими. Выигрыш — три свойства, организующие остальной файл:

- **Обобщение / масштабирование** — новые случаи садятся тонкими композициями, система масштабируется на
  новые сценарии без форка стека.
- **Производительность** — границы стабильны и схлопываются только по замеру, абстракция не съедает
  скорость незаметно, а оптимизация остаётся безопасной.
- **Стабильность / воспроизводимость** — единое владение способностями и сквозными инвариантами держит
  изменение в его blast-radius, а результаты — консистентными.

Эти законы ЗАОСТРЯЮТ, не заменяют, always-on правила спайна. Правило спайна, которое каждый закон
расширяет, помечено инлайн как `[spine: <правило>]`; пункт без тэга — net-new.

## A. Обобщение и масштабирование

**A1 — Владение следует графу зависимостей, не имени или ярлыку уровня.** Способность принадлежит САМОМУ
НИЖНЕМУ модулю, который может её выразить, завися только от модулей ниже. Реальные рёбра зависимостей
(imports / requires / link-рёбра) — авторитет; числовые «уровни» или ИМЕНА директорий — лишь
вспомогательная подсказка (A1 тем самым *инвертирует* организацию по именам директорий — рёбра важнее
имён). Восходящая или циклическая зависимость должна быть ПОЙМАНА репо-стандартным ГЕЙТОМ,
настроенным на падение, — build, lint/import-graph-чек, валидатор или CI (чем экосистема может
обеспечить; не каждый язык роняет build на цикле). Этот гейт, а не соглашение, и есть enforcement.
[spine: SOLID reminder, Ownership / extension-seam hygiene]

**A2 — Адаптер — поверхность правок; backend стабилен ПО УМОЛЧАНИЮ.** Новый сценарий, метод или
интеграцию добавляй РЕДАКТИРУЯ тонкие связующие слои — composition (проводка), coupling и адаптеры
интерфейс-листа — СНАЧАЛА, НЕ залезая в стабильный backend-модуль. Чтобы поддержать новый случай, ты
обычно должен править адаптер / composition / интерфейс; backend не должен требовать
сценарно-специфичной правки. ИСКЛЮЧЕНИЕ: правка backend легитимна, когда новый случай вскрыл
НЕДОСТАЮЩУЮ ОБОБЩЁННУЮ способность или смещённый шов — при условии, что правка обобщает (не
сценарно-специфична) и существующие потребители защищены. Запах — это *сценарно-специфичная* правка
backend; значит шов отсутствует или не там — добавь или сдвинь адаптер, не форкай backend.
(Универсальность-следствие A6: A6 говорит ГДЕ живёт контракт; A2 — что адаптер поверх него и есть то,
что ты редактируешь.) [spine: Ownership / extension-seam hygiene, Change-surface minimization,
Blast-radius test]

**A3 — Generic-движок не называет конкретного потребителя.** Переиспользуемый движок / сервис / утилита
зависит только от своих абстрактных входов и не называет конкретную фичу/метод в символах, импортах или
рёбрах зависимостей. Берёт абстрактный вход (собранную структуру, `apply`/strategy-колбэк,
типизированный запрос) и возвращает результат. Новый потребитель становится тонким скриптом, ПОСТАВЛЯЯ
этот вход — никогда не добавляя вариант движка или ветку метода внутри него. [spine: SOLID reminder]

**A4 — Новый вариант — это плагин + тонкий сценарий, никогда не параллельный силос.** Новая фича / метод /
вариант расширяет СУЩЕСТВУЮЩИЕ модули плагином на нужном слое плюс тонким сценарием над существующими
швами. Не должен порождать параллельную копию всего стека. Если «новому варианту» нужна своя копия общей
инфраструктуры (свой parse / storage / transport / geometry), слоистость неверна — отсутствует шов,
который надо было скомпоновать. [spine: Blast-radius test, Reuse before hand-rolling, Mechanism
inventory before new paths]

**A5 — «Тонкий» определяется относительно слоя, не числа строк: тест второго потребителя.** Точка входа
(CLI / app / handler / job) владеет ТОЛЬКО process-binding — argument / env / file / exit / IO-политика.
Каждое решение, переживающее смену точки входа — выбор, размеры, выбор стратегии, контроль sweep /
retry, гейтинг результата — это библиотечная способность и живёт в библиотеке. Тест: если ВТОРОЙ точке
входа (тулзе, тесту, будущему GUI) понадобилось бы то же решение — это НЕ проводка, оно принадлежит
библиотеке. [spine: Change-surface minimization, Ownership / extension-seam hygiene]

**A6 — Dependency inversion: контракт на стабильной поверхности, никогда не разворот.** Когда нижний
модуль должен быть ВЫЗВАН верхним, но не может ЗАВИСЕТЬ от него, определи узкий КОНТРАКТ на СТАБИЛЬНОЙ
поверхности, на которую обе стороны могут зависеть без разворота направления зависимости — сам нижний
модуль, или нейтральный contract / interface-модуль ниже обоих — и ИНЖЕКТИРУЙ реализацию сверху.
Контракт НЕ всегда живёт «в самом нижнем модуле»: service-контракты, plugin-API, schema-реестры и
role/agent-контракты часто живут на нейтральной стабильной поверхности, которую импортируют обе стороны.
Инвариант, который держится ВЕЗДЕ: реализационно-тяжёлые / приватные модули НЕ должны импортироваться
через слои — кросс-слойное потребление легально только против интерфейс-листа без нисходящих рёбер;
ребро в приватный/внутренний модуль соседа через band — презумптивно силос-течь. [spine: Interface and
encapsulation hygiene, SOLID reminder]

**A7 — Раздели способность по уровням ПРЕЖДЕ чем назвать что-то копией (graduate-the-core).** Разложи
способность по уровню абстракции. Самый нижний чистый, зависимостно-лёгкий CORE (без фича / transport /
storage-зависимостей) — единица одного владельца, и его НАДО переиспользовать (import / reference /
generate из одного источника), никогда не перепечатывать руками. Оркестровка этого core потребителем
над конкретной раскладкой — пер-потребительский GLUE — не копия, но он должен ЗВАТЬ core, никогда не
перевыводить. Потребность «продакшн не должен зависеть от sandbox / эксперимента» удовлетворяется
ГРАДУАЦИЕЙ core в его модуль-владелец СНАЧАЛА (чтобы продакшн переиспользовал градуированный core),
НИКОГДА не переписыванием ради ухода от зависимости. Переписать градуированный core «чтобы избежать
зависимости» — дефект, не изоляция. (Hard-boundary исключение: см. C1.) [spine: No logic duplication,
Reuse before hand-rolling]

## B. Производительность

**B1 — Граница — link/call-граница по умолчанию; схлопывай ради СКОРОСТИ только по замеру.** Шов — это
link/call-граница по умолчанию. Схлопывание / инлайнинг шва РАДИ ПРОИЗВОДИТЕЛЬНОСТИ разрешён ТОЛЬКО
когда (a) ЗАМЕР ПРОФАЙЛОМ показывает его на измеренно-критическом пути И (b) схлопнутая единица остаётся
одним связным владельцем — её владение, lifecycle, очистка ресурсов, контракты и тесты остаются внутри
одного модуля. Никогда не схлопывай шов ради скорости спекулятивно («может, инлайном быстрее» без замера
— нарушение, не оптимизация). Это управляет ТОЛЬКО производительностно-мотивированным схлопыванием —
обычные рефакторы, двигающие код ради ясности, управляются A1/A2, не B1. Без замера core остаётся
ВЛАДЕНИЕМ слоя, держащего цикл, а шов остаётся грубым. [spine: Pre-fix diagnostic gate (профайл перед
изменением рабочего пути ради скорости)]

**B2 — Не дели измеренно-критическую или порядко-чувствительную последовательность через границу.**
Горячий внутренний цикл, порядко-чувствительная редукция / аккумуляция, одна транзакция или стадия
streaming-пайплайна остаётся в ОДНОЙ единице; шов сидит на её входе / выходе, никогда в середине.
Деление через границу и стоит производительности, и (для порядко-чувствительных редукций) может менять
результаты — см. C1.

**B3 — Тяжёлый контекст продевай только на грубых границах.** Контекст исполнения, хэндлы, соединения и
большой конфиг передаются на ГРУБЫХ публичных границах, никогда не перепродеваются на каждой внутренней
итерации (record / row-данные, текущие сквозь пайплайн, — не «тяжёлый контекст»: речь про ambient-хэндлы,
не payload). Поитерационная прокладка контекста — и стоимость, и течь связности.

## C. Стабильность и воспроизводимость

**C1 — Один владелец сквозного инварианта.** Сквозной инвариант, который должен оставаться глобально
консистентным — режим-предикат (напр. детерминированный / strict-режим), каноничный порядок,
разделяемая константа, смысл флага, калибровочная таблица — имеет РОВНО ОДНОГО владельца, которого каждый
потребитель ЗОВЁТ. Ни один модуль не перерешает его, и ни один не переопределяет / не перепечатывает
«чтобы остаться консистентным» — это переопределение И ЕСТЬ баг (копии дрейфуют). HARD-BOUNDARY
ИСКЛЮЧЕНИЕ: дублированное *представление* через process / language / ABI / generated-code /
database-schema / external-protocol-границу разрешено ТОЛЬКО когда оно выведено из одного owned-источника
(codegen, общая схема) или защищено drift / contract-гейтом, падающим на расхождении; неконтролируемая
ручная перепечатка через такую границу остаётся багом. Воспроизводимость (bit-identical или
contract-identical результаты) зависит от этого единого владения. [spine: No logic duplication]

**C2 — Конфиг и управление — входы верхнего слоя: парси один раз наверху, инжектируй вниз.** Окружение
процесса, опции командной строки, deck / scenario-селекторы, метки валидации, пути файлов и
переключатели режима — входы ВЕРХНЕГО слоя. Верх (app / composition / handler) парсит их ОДИН раз в
типизированные неизменяемые config-структуры, execution-policy-объекты или strategy-колбэки и передаёт
уже-разрешённые значения ВНИЗ. Нижний модуль, читающий `getenv` / cmdline-политику / глобальный
scenario-режим — это ВОСХОДЯЩАЯ УТЕЧКА УПРАВЛЕНИЯ, даже когда ребра зависимости нет. Единственное
исключение — документированная диагностическая / observability-инструментация без business / semantic /
output / persistence / security / control-flow-эффекта, во владении support / observability-слоя —
никогда обычная нижнеслойная доменная логика. [spine: Determinism and ambient-input control,
Anti-hardcoding]

**C3 — Стабильность backend — это свойство стабильности (тот же шов, что A2).** Backend-модули
(foundation, generic-движки, storage, transport) поглощают новые сценарии через адаптеры / composition
(A2); *сценарно-специфичная* правка backend расширяет blast-radius каждого будущего изменения. Это
stability-прочтение A2 — при конденсации в правила ролей A2 и C3 — ОДНО правило с двух-исходной
аннотацией (обобщение + стабильность), не две проверки. [spine: Change-surface minimization, Blast-radius
test]

**C4 — Разделяемая тест-поддержка — единица одного владельца, test-only.** Generic тест / validation-
поддержка — фикстуры, структурные генераторы, загрузчики golden-артефактов, эталонные решения, generic-
харнессы — единица одного владельца под TEST-ONLY деревом, параметризованная ПРОДАКШН-КОНТРАКТОМ
(интерфейс, не конкретная реализация), изолированная от продакшн-таргетов и НИКОГДА не размещённая внутри
тестов одной реализации. Следствие: удаление или демоция реализации должны быть ЧИСТЫМ DELETE с нулём
правок в тестах других реализаций. Фальсификация: если файл тест-поддержки импортируется / линкуется
тестами реализации B, живя под реализацией A, он размещён неверно. (По-настоящему net-new — в спайне нет
правила про владение тест-поддержкой.)

**C5 — Grandfathered-долг отслеживается, никогда не благословляется молча.** Принятый текущий долг,
явно благословлённый задокументированным решением («example-адаптер», временная копия), отличается от
правила для НОВОЙ работы. Записывай его как grandfathering-запись, называющую ВЛАДЕЛЬЦА, СКОПЕ,
EXPIRY / триггер пересмотра и явный «no expansion»-текст; отслеживай открытые нарушения в ранжированном
DRIFT BACKLOG отдельно от правила, и (где у репо он есть) в его реестре decisions / grandfathering.
Grandfathered-пункт НИКОГДА не лицензия на новые нарушения той же формы. [spine: Hypothesis disclosure
discipline (WORKAROUND labeling)]

## Защищаемые свойства (не должны регрессировать)

Структурное изменение должно сохранять эти инварианты — у каждого есть названный владелец и
проверка-зонд; регрессия любого — блокирующий finding:

- **Ацикличный, только-нисходящий граф зависимостей** (A1) — зонд: репо-стандартный build / lint /
  import-graph / CI-гейт.
- **Нет нижнеслойных ambient-чтений** (C2) — зонд: `grep getenv` / cmdline в нижних модулях не даёт
  недокументированного хита.
- **Один владелец на сквозной инвариант** (C1) — зонд: grep операции/константы; одно определение,
  остальные зовут.
- **Нет неотслеживаемых дублированных представлений** (A7, C1) — зонд: дубли только за codegen-источником
  или drift-гейтом.
- **Точки входа не держат решение второго потребителя** (A5) — зонд: каждое решение в app/tool не имеет
  близнеца, нужного второй точке входа.
- **Тест-поддержка удаляется чисто** (C4) — зонд: удаление реализации не правит другие тесты.

## Проверяемый чеклист (каждое структурное изменение проходит; NO — блокирующий finding)

Каждый пункт НАЗЫВАЕТ единого владельца и ПРОВЕРКУ-ЗОНД (grep / build / lint / validator / CI-чек,
ловящий нарушение):

- [ ] Новая способность садится в свой единственный модуль-владелец; нет второй копии (grep
      символа/операции, не имени).
- [ ] Каждое ребро зависимости строго вниз по графу или к интерфейс-листу; нет ребра в
      приватный/внутренний модуль соседа через band; нет восходящего/циклического ребра — поймано
      репо-стандартным build/lint/import-graph/validator/CI-гейтом (A1).
- [ ] Ни один generic-движок include/символ/ребро не называет конкретного потребителя/фичу/метод (A3).
- [ ] Ни одна единица точки входа не держит решение, нужное второй точке входа (A5).
- [ ] Любая способность, определённая в ≥2 местах, где нижний core можно переиспользовать, разложена:
      core переиспользован, только glue пер-потребительски (A7) — нет копии-ради-ухода-от-зависимости.
- [ ] Новый сценарий добавлен правкой адаптера/composition/интерфейса, НЕ сценарно-специфичной правкой
      backend (A2/C3); правка backend, если была, обобщила недостающую способность и защитила
      существующих потребителей.
- [ ] Ни один нижний модуль не читает env/CLI/глобальную scenario-политику; конфиг парсится один раз
      наверху и инжектируется вниз (C2) — `grep getenv`/cmdline в нижних модулях не даёт хита, кроме
      документированно-диагностического, support-owned, без business/semantic/output/security/control-flow
      эффекта.
- [ ] У каждого сквозного инварианта/предиката/константы один владелец, которого все зовут; ни один не
      переопределён / не перепечатан «чтобы остаться консистентным», кроме hard-boundary-представления,
      выведенного из одного источника или защищённого drift-гейтом (C1).
- [ ] Любое схлопывание шва горячего пути РАДИ СКОРОСТИ ссылается на замер профайла и держит одного
      связного владельца (B1); ни один шов не делит измеренно-критическую/порядко-чувствительную

## Термины и сокращения

- **слой / модуль** — единица одного уровня абстракции с узким интерфейсом и одним владельцем.
- **силос** — фича как большая независимая программа с приватными копиями общих слоёв (анти-паттерн).
- **core / glue (A7)** — нижнее чистое ядро одного владельца (переиспользуется, не перепечатывается) vs
  пер-потребительская оркестровка над ним.
- **dependency inversion (A6)** — контракт определён на стабильной поверхности, на которую обе стороны
  могут зависеть, реализация инжектируется сверху.
- **interface leaf (интерфейс-лист)** — interface / protocol / contract-модуль без нисходящих рёбер
  зависимостей, безопасный для зависимости через слои.
- **adapter / binding / composition (A2)** — тонкая поверхность правок, где проводятся новые сценарии,
  поверх стабильных backend'ов.
- **dependency graph / DAG** — ориентированный граф зависимостей модулей (imports / requires / link-рёбра);
  должен быть ацикличным с рёбрами вниз.
- **сквозной инвариант (C1)** — значение или правило, которое должно оставаться идентичным во многих
  модулях (режим-предикат, каноничный порядок, разделяемая константа), и потому требует ровно одного
  владельца.
- **upward control-flow leak (восходящая утечка управления, C2)** — нижний модуль, читающий ambient-
  политику (env / CLI / глобальный режим), которую должны были инжектировать сверху, даже когда ребра
  зависимости нет.
- **hard boundary (жёсткая граница)** — process / language / ABI / generated-code / DB-schema /
  external-protocol-граница, через которую терпимо выведенное-из-одного-источника или drift-gated
  дублированное представление.
