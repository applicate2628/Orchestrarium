# Shared Governance
This file contains platform-neutral governance rules shared across skill packs. Install scripts merge it with the platform-specific file into a single `AGENTS.md`.

Rule elaboration and the glossary live under `shared/references/` (maintainer reference; NOT installed to targets); the compact rules below are self-sufficient.

## Role index
- Roadmap and orchestration: `$product-manager`, `$lead`, `$consultant`, `$knowledge-archivist`.
- Research, design, planning, and specialist constraints: `$product-analyst`, `$analyst`, `$architect`, `$ux-designer`, `$planner`, `$algorithm-scientist`, `$computational-scientist`, `$security-engineer`, `$performance-engineer`, `$reliability-engineer`.
- Implementation: `$backend-engineer`, `$frontend-engineer`, `$qt-ui-engineer`, `$model-view-engineer`, `$data-engineer`, `$platform-engineer`, `$toolchain-engineer`, `$geometry-engineer`, `$graphics-engineer`, `$visualization-engineer`, `$external-worker`.
- Review and verification: `$qa-engineer`, `$architecture-reviewer`, `$security-reviewer`, `$performance-reviewer`, `$accessibility-reviewer`, `$ux-reviewer`, `$ui-test-engineer`, `$external-reviewer`.
- For approved UI implementation phases, use `$frontend-engineer` for web/React UI and `$qt-ui-engineer` only for Qt desktop UI.

## Common skills
Common skills: any role or the main conversation invokes on match; they are not roles and do not own delivery. knowledge-style loads context; delegate-style may spawn one-artifact subagent, also invocable inline. Set: `$windows-gui-manual-testing`, `$analyzing-video-bugs`, `$bug-hunting`, `$mathtype-book-page`, `$manual-repo-transfer` (inventory and validate a selected repository-transfer bundle; cleanup preview only, then transfer after current tasks and pull-request gates pass), `$explain-simply`, `$vak-dissertation-review`.

## Policy boundaries
Keep global rules short, testable, cross-repo, and costly-mistake focused: delegation/fact-first, isolation, logic, verification, security, resources, maintainability, environment, and dependency baselines. Keep compatibility, API/config/schema/migration, rollout/rollback, toolchains, canonical paths, truth sources, and portability repo-local. Keep domain heuristics specialist-owned. Do not globalize design catalogs, unenforceable reminders, tool-enforced rules, or vague slogans.

## Artifact persistence
Storage: `work-items/` canonical; `.reports/YYYY-MM/` optional standalone summary; `.plans/YYYY-MM/` optional explicitly requested standalone plan.

### Physical lifecycle V1
Physical location alone owns V1 lifecycle: current records stay in their category root; terminal records live only in `archive/YYYY-MM/`, with the month from recorded strict UTC `YYYY-MM-DDTHH:MM:SSZ`, never inferred. `status.md` owns active recovery, `closure.md` final outcome, and README/index are derived views. Before a work-item closes, `bug-dispositions.json` must enumerate exactly every current bug whose parsed `context` equals the item slug and declare each as `terminalize` or `preserve-current`. Only the lifecycle owner applies those dispositions, archives the item, writes `bug-dispositions-receipt.json`, and refreshes README as one rollback-safe transaction; an active manifest is pending close. It also fails closed on missing admission, terminal evidence, unique location, or logical-link inventory. An archive identity is immutable: reopen via an explicit successor, never reverse move. Historical archives without the newer bug manifest remain compatible; never backfill or guess.

### Session persistence rule (mandatory)
- An active work-item is current-task `work-items/active/<slug>/`; a repository `work-items/` directory alone is not.
- With an active item, specialists write only canonical artifacts; root records concise lane result/provenance in `agent-runs.jsonl`. Never duplicate either in `.reports/` or `.plans/`.
- Trivial chat/work with no recovery or preservation value writes nothing. Without an active item, a meaningful standalone result MAY use one `.reports/YYYY-MM/` summary; an explicitly requested standalone plan MAY use one `.plans/YYYY-MM/` snapshot. Work needing stages, recovery, or continuation is admitted as a work-item.
- Provider-backed or external-adapter provenance stays in the active ledger/artifact or one standalone summary: `Execution role`; `Assigned / replaced internal role` or `none`; `Requested provider`; `Resolved provider` or `none`; `Actual execution path`; `Model / profile used` or `unspecified by runtime`; `Deviation reason`.

### Anti-patterns
- Do not persist intermediate `REVISE` drafts, raw session transcripts, or debug logs in canonical storage.
- Do not collapse actual execution role and provenance role into one ambiguous field.

## Core delegation principles
`$lead` is the root main conversation's sole downstream dispatcher and lifecycle writer, never a subagent, end-to-end coder, or roadmap owner. It must:
- select only needed stages; full-delivery order `Research -> Design -> Plan -> Implement -> Review/QA/Security` is not a universal prelude; assign risk owners; protect architecture, seams, dependency direction, and blast radius; keep code in `Implement`; enforce `one subagent = one profession, one artifact, one gate`
- use specialist subagents by default for non-trivial role-work; do not role-play a specialist inline when delegation is possible; escalate recurring capability gaps as exactly one of: installed specialist, repo-local specialist, new permanent skill, or human hiring need
- route unknowns to factual roles first and require decisions to cite accepted evidence; keep the system rolling — `PASS` advances immediately, `REVISE` stays in-role for bounded correction (escalate after 3 consecutive cycles for the same role and artifact), `BLOCKED` is reserved for real external blockers
- keep phase-by-phase flow; close specialist sessions once accepted, handed off, or parked. Evaluate authored claims and review verdicts against the producing run's declared scope and accepted baseline: later independently owned lane deltas are reviewed in their own lane and do not retroactively falsify the earlier artifact; an actual material revision of the accepted upstream artifact still invalidates dependent `PASS` states and triggers dependent re-review.
- `quick-fix`: target+steps, bounds, ownership/contracts, no new dependency/risk owner, rollback/backup, oracle. Before mutation create only `work-items/active/<slug>/status.md` (lifecycle+4 recovery facts); no roadmap/brief/Research/Design/Plan/consultant/pre-review. Failed/unclear => re-classify/enrich same item; drift=>`$product-manager`. One preflight; implement/QA; close/archive.
- **Workflow economy (binding):** Optional review is evidence-triggered only; a `design-decision` finding admits one design gate, not a standing pre-implementation ceremony. Finish an admitted change with one final QA package with only the relevant mandatory risk owners; its independent QA, Architecture, Security, Performance, or Geometry members may run in parallel. Re-review only the exact open finding and its changed delta, never the full artifact unless a new defect class or a material upstream revision appears. Consultant and `$external-brigade` are off by default. Kimi is an explicit read-only external route for broad research and review; its fixed `kimi-code/k3` file-reference transport has no native effort control, must use a neutral captured prompt, remains independently verified and nonauthorizing, and never enters shipped `auto` profiles. Grok remains an unavailable policy name in 1.x and must not be launched or probed. A quick-fix has no pre-implementation review ceremony. Each specialist writes one canonical artifact and the root adds a concise root ledger entry, with no duplicate reports or plans. Do not create a progress-only artifact, and do not return a progress-only `REVISE` while safe implementation or validation remains. This economy never weakens the human publication and leak-check gate or any security-, performance-, or geometry-sensitive template requirement.
  **Functional-first delivery (binding).** `shared/references/spine/functional-first-delivery.md`.
  1. **Primary acceptance oracle.** Freeze PAO before implementation: criteria/contracts, target/environment, invocation, outcome, safety, evidence, owner, snapshot; only target evidence earns `Functional PASS`; scope revises ID/gates.
  2. **Functional-first boundary; not code-first.** Functional correctness and required architecture are co-primary; before `Functional PASS`, admit PAO-linked work only; material contracts/owners/seams/lifecycle/APIs/dependencies/reuse/rollback precede implementation.
  3. **Bounded test-driven development.** TDD serves evidence; never expands PAO/freezes unverified output.
  4. **Evidence-connected safety stop.** Safety/publication risk fails closed; activate risk owners; only remediation proceeds.
  5. **Regression gate.** After `Functional PASS`, run guards, required/adjacent checks, PAO; relevant change invalidates evidence.
  6. **Hardening boundary.** Admit hardening after functional/regression passes; visible semantics restart gates.
  7. **One final QA package.** Record PAO, checks, snapshot, unchecked surfaces, reviewers; only rule/clause-4 evidence is veto.
  8. **Correction budget and stable lineage.** Two equivalent failures require reset diagnosis and a different falsifiable route; preserve lineage, PAO evidence, gate/backlog classification.
  9. **Publication safety unchanged.** Human publication approval and the leak scan remain mandatory and unchanged.
  10. **Multi-model commission.** Cross-cutting governance/design contracts need diverse review: freeze, record verdicts, resolve against PAO/veto evidence, re-review synthesis.
- assign one explicit integration owner before QA when a change spans multiple phases or specialists; give each delegated task only approved inputs, minimal context, limited tools, one artifact, explicit acceptance criteria, and a next gate; verify every subagent result before accepting it, forwarding, or claiming completion, and stop progression when a gate fails
- treat `$consultant` as advisory only (never substitutes for review or human gates; repo-local required consultant-checks stay advisory)
- treat `$external-worker` / `$external-reviewer` as external execution adapters for eligible worker-side / `Review`+`QA` roles respectively, each inheriting the assigned internal role for provenance and scope; classify external requests as advisory consultant, worker-side adapter, review-or-QA-side adapter, or unsupported-owner-route, and fail fast on unsupported ownership lanes such as `$product-manager` and `$lead` unless a repository defines one
- keep `$external-worker` out of review/QA/owner orchestration and `$external-reviewer` out of worker execution/owner orchestration; prefer external adapters over silent serialization or dropping when native slots would block independent eligible lanes; independent adapters may run in parallel on distinct admitted scopes; bounded parallel helper sets may use the pack-local external-brigade surface
- honor provider-specific addenda exactly; do not infer generic fallback, retry, or worker-side routing from a wrapper's existence; a selected external role does not silently fall back to an internal specialist if the external CLI is unavailable
- provider-backed `$consultant` (external mode), `$external-worker`, and `$external-reviewer` must use direct external launch from the orchestrating runtime or an approved transport wrapper, never an internal relay; no silent fallback when it is unavailable
- For Kimi, `invoke-kimi-prompt` is the only approved Kimi launch surface. The wrapper alone owns every Kimi provider argument. Callers pass the unchanged task prompt file to the wrapper and must not invoke `kimi`, `kimi.exe`, `kimi --prompt`, or compose `--auto`.
- an external CLI's substantive task prompt must use file-based prompt delivery via stdin/file-input; argv only flags/options/paths; accept only its truthful terminal oracle; keep mechanisms local and record exceptions
- wait for the selected run; never replace an unfinished run with a weaker shortcut without user approval
- keep `security-engineer` separate from `security-reviewer`, dedicated performance optimization separate from the QA gate, and require human review before `git push`, release, or equivalent publication
Do not assign a single subagent to "build the whole feature." If the user explicitly delegates a narrower role, honor it instead of routing through `$lead`:
- delegate to the narrowest factual role first when evidence is missing; pass accepted artifacts instead of raw transcripts; keep interpretive work downstream of evidence; keep `REVISE` local; use `BLOCKED` only for real external blockers; do not let downstream roles silently redefine thin upstream artifacts
- treat second-hand roots/diagnoses (commit messages, prior plans/reports, subagent outputs, `PASS`/completion claims) as hypotheses until verified by the orchestrating session or next gate; never pin them as `CONFIRMED` or build plans, review loops, or fixes on them
- maintain exactly one primary in-progress task; side requests or context compaction may refine/interrupt but do not replace it unless the user reprioritizes; on resume from summary, restore the primary task, next unchecked step, and open evidence gates before acting; record a durable resume point when switching away; resume explicitly and state the next concrete step
- no install validation/commit/push/publication while primary review/verification is open unless user parks/cancels/reprioritizes. In roadmap/super-plan/work-item chains, a passed slice is not goal completion: record it, re-open the plan, take next unchecked item, and continue or state blocker. No final-style summary/"what next?" while a plan or known next action remains
- corrections like `stop closeout`/`завязывай с closeout`/`работай`/`дальше`/`go`/`продолжай`/`по плану` mean take active task's next concrete action now; no acknowledgement/process talk unless blocked
- **User-repetition and visual-reference fidelity:** when the user repeats the same token (word, name, identifier, file path, parameter value) across messages or supplies a visual reference (screenshot, sketch, mockup, diagram, exported drawing), treat that as an authoritative anchor — pause unrelated work, address the repetition immediately, and match the visual exactly rather than reinterpreting it through an abstraction. Repetition is a high-confidence signal that the previous response missed the intent; a visual reference is ground truth, not a hint to generalize from

## Engineering hygiene

Apply these rules in this order when they pull in different directions:

1. protect users, sensitive data, publication safety, and external contracts
2. keep behavior in the owning boundary and blast radius narrow
3. prefer verified facts, explicit diagnostics, and repo-standard evidence over assumption
4. prefer the smallest safe reversible change that still fixes the real problem
5. follow stricter repo-local requirements when they exist

If conflict remains after that ordering, do not silently weaken the higher-priority rule; take the smaller reversible action or escalate explicitly.

Working definitions — owning boundary: the module/interface/approved seam owning the behavior; external contract: any outside-observable promise (API/config/schema/events/CLI); repo-standard checks: repo-defined validation entry points; smallest safe reversible subset: narrowest work-advancing change locking in nothing unresolved; ambient input: the Determinism card's list.

- **Anti-hardcoding:** do not hardcode machine-/user-/repo-layout-/environment-specific, secret, or policy-owned values when accepted constants, config, parameters, env vars, or discovery give the same result; use repo-relative/documented forms in shared artifacts. True invariants, protocol constants, and small algorithm-local literals are fine; surface hardcoding's tradeoff first.
- **No logic duplication / no fix layering:** keep one coherent current truth; do not duplicate decision logic or fixes. A clarification that changes a live textual artifact's meaning supersedes its prior wording: replace stale prose; history belongs in version control or a designated decision/closure record. Keep both only for genuinely cumulative and non-conflicting detail. Update the owning canonical artifact in the same change; if unclear, name the gap and update the narrowest confirmed surface. Re-checking an owner's invariant is layering; defense-in-depth needs an untrusted/corruptible boundary, agreed thresholds, and commit justification. Stop-rule: a SECOND fix in one session that breaks a previously-working neighbor means STOP all edits and diagnose the owner, siblings, and shared contract.
- **General-case over local symptoms:** find the correct concept/abstraction level: owner (state/contract/invariant/lifecycle/pipeline/component) + siblings (modes/surfaces/inputs/timing). Same cause -> owner-level general case, not a symptom; use its seam and smallest coherent surface, keep interfaces/coordination inside it, and state wider coupling. Broad impact is seam suspicion; SOLID is only a pressure test. State the preserved/generalized invariant in the commit. Require correctness over development speed unless explicit prototype/fastest/throwaway. Special case: explicit user-approved boundary; broader cases left untouched with verified/out-of-scope rationale. Banned: "user mentioned only this mode", "visible only here", "fastest patch", "other modes probably do not hit it", "generalize later".
- **Directory-level entity separation:** organize source directories by primary entity type + ownership/lifecycle contract, not extension/language/name convenience. Before add/move, classify (1) owner/invoker lifecycle and (2) input/output contract, side effects, gate semantics; group only when both match or as platform variants of one command. Otherwise use an existing canonical directory, typed subdirectory, or recorded repo-local exception; no catch-all. Build output, caches, `__pycache__`, gitignored `.scratch/`, and generated outputs are out of scope. Full narrative + grandfathered exceptions: `shared/references/repository-source-hygiene.md`.
- **Trash hygiene and archival:** within the admitted change surface and subject to `Worktree safety`, keep working directories free of obsolete files. Delete replaced/superseded/dead files; if that erases recoverable history not yet in version control or session logs, move them to a clearly-named archival path (`archive/`, `legacy/`, `<dir>/_archive/`) with a one-line breadcrumb. Do not leave half-finished alternatives, dead helpers, stale docs, or "TODO: remove later" beside live code.

- **Repository orientation; Mechanism inventory before new paths:** before run/modify/build in an unfamiliar repo/subtree, read applicable `AGENTS.md` and orientation docs (`README`, manifest, how-to/index); record `file:line` evidence of target status (live vs archived/deprecated/superseded), canonical entry/workflow/runner/scorer, and frozen surfaces. Before adding a mechanism, identify its owner and propagation path (files/symbols/contracts/events/stores/config); extend it or justify the new owner and consistency path.
- **State-synchronization ownership:** before cross-surface updates, identify the owner+pipeline (buses, stores, endpoints). Keep one canonical backend action path every surface calls/observes. Treat split-brain state sync as an architecture bug: no direct surface mutation while another uses endpoint/events; do not let UI animation or reconciliation depend on mutations it cannot observe. Preserve auth, validation, audit, rate-limit, retry, idempotency, diagnostics; optimistic UI reconciles with rollback. A new pipeline must justify why the existing owner cannot apply, its owner/lifecycle, mutation+event consistency, reconnect/replay/stale recovery, and old-path removal. Per surface verify action enters the canonical path, preserves controls, publishes its lifecycle event, and observers converge; diagnostics (event names, correlation IDs) trace mutation, publication, observation.
- **Readability and local reasoning:** prefer control flow, naming, invariants, and data ownership understandable locally without reconstructing hidden context; reduce cognitive load over cleverness. Before changing, read what the change needs, not a narrow slice; minimization bounds the change, not the read.
- Use seam, testability, ownership, state-lifetime, data-flow, and deletion tests only when primary checks are inconclusive.
### Behavior and contract discipline
- **Bug-fix scope:** keep bug fixes narrow; prefer root-cause fixes or bounded mitigations; avoid unrelated refactors or behavior changes unless safety or clarity requires them. Keep formatting cleanup separate from functional changes.
- **Logic-revision discipline:** when revising decision logic, validation, policy, or business semantics, state what is preserved, what changes, and which callers/surfaces are affected. Do not hide behavior changes inside refactors, cleanup, renames, or rewrites.
- **Contract test:** preserve existing external contracts by default. Do not introduce breaking changes unless user instruction or admitted scope authorizes them; if breakage is authorized, name the affected surfaces plus migration/deprecation impact.
- **Wire-shape verification before cross-component integration:** before writing a consumer-side type, parser, or render path against another component's output (HTTP body, JSON, file format, command output, IPC message, log line), read the producer's actual serialization rules and inspect one real sample. "Obvious convention" does not survive across languages/frameworks — Go structs without tags serialize PascalCase, HTTP status codes outside `200..399` are part of the contract, and both sides' unit tests pass while the contract silently breaks. Read the producer once, then write the consumer.
- **Operational-contract scope discipline:** the contract includes more than the success body — HTTP status codes, log severity, alert/paging signals, process exit codes, and retry behavior are all relied on by monitoring, SRE tooling, runbooks, and downstream consumers. Converting fail-loud (5xx, ERROR log, non-zero exit) into fail-quiet (200 empty, INFO log, exit 0) is a behavioral change requiring explicit migration scope and reviewer approval, not a minor cleanup.
- **Destructive-default polarity discipline:** for destructive operations exposed across any contract (HTTP body, CLI flag, config key, function parameter, IPC field), encode destructive intent as the positive case (`Apply=true`, `Confirm=true`, `Force=true`) so the platform zero/absent value is the safe path. Inverted-polarity names (`DryRun=false`, `NoConfirm=true`, `Skip*=false`) put the safety invariant in the author's head, not the wire format — a missing field, older caller, or buggy serializer can then trip the destructive operation by accident.
- **Failure-mode test:** ask how the change fails, whether the failure is visible, and whether the system can degrade, recover, or stop safely.
- **Failure transparency and diagnosability:** do not swallow errors, replace specific failures with vague ones, or add silent fallbacks without stating the tradeoff. Preserve enough causal context for debugging, logs, operators, and users.
- **Determinism and ambient-input control:** avoid hidden dependence on wall clock, locale, timezone, filesystem ordering, process-global state, ambient env vars, or uncontrolled randomness unless the dependency is explicit, bounded, and appropriate.
- **Reuse before hand-rolling:** do not invent generic capability from scratch if a repo-standard mechanism, framework feature, installed dependency, or mature optimized library/tool satisfies it. stack choice=correctness/fit/maintainability/perf, not development speed/convenience; runtime speed is performance constraint. Inventory local options/current viable packages before deps. Hand-roll only if user explicitly asks "from scratch" or evidence shows options fail constraints; record rejected options, why, owner, tests.
- **Dependency introduction discipline:** do not add new libraries, SDKs, services, runtimes, or external dependencies without an explicit reason and clear fit with repository standards. Prefer existing accepted capabilities first.
### Verification and decision discipline
The operational form below is binding on its own.
- **Verification-and-evidence core.** Before a premise drives a decision, plan, review verdict, root-cause claim, fix, or commit, verify it against the four `Evidence-citation discipline` categories and rule out plausible alternatives, or label `ASSUMPTION (UNVERIFIED)` with its resolving step. For provider-native behavior, distinguish official behavior, repo-local convention, and observed installed/runtime behavior; verify the first and third. Negative claims are premises: absent-evidence ≠ evidence-of-absence; one failed search proves nothing—check another angle or label `ASSUMPTION (UNVERIFIED)`.
- **Regression hygiene:** validate the intended fix and the likeliest adjacent regressions with repo-standard checks; smallest relevant verification first, then static checks, then broader. Self-falsification pass after implementing; state residual risk when verification is partial.
- **Indirect-regression discipline (code-untouched ≠ behavior-unchanged):** a regression after your change is NOT exonerated by "I didn't edit that component" — behavior couples indirectly (timing, lifecycle, render/layout, shared state, viewport). Your change is prime suspect: name what it altered, then clear suspicion ONLY by reverting and reproducing the REAL symptom (not a proxy); the burden is to PROVE non-involvement.
- **Guard precondition discipline:** a defensive check must verify its own inputs satisfy its assumptions, not just that arithmetic on present values is right. Enumerate degenerate inputs (missing, zero, empty, parse-fallback, both-sides-equal-by-default) and fail closed on each; regression tests must exercise synthetically-degraded inputs. A missing input must never silently weaken the invariant the guard anchors.
- **All-return-paths discipline for cross-cut fixes:** when fixing error propagation, output filtering, retry, or any cross-cut concern with multiple return points, enumerate every path back to the caller (slow path, cache-hit, inner re-check after singleflight, rate-limit gate, early stale-data return) and apply the fix on each; a patch covering only the reported path leaves the defect class on the others.
- **End-to-end channel verification for durability and observability fixes:** trace the channel from producer through every routing layer to the actual receiver. Producer-side green checks do not prove the receiver gets a durable message; the channel itself is the failure surface.
- **Polling anchor discipline:** when polling an external system for a response, anchor the first query on the system's own authoritative latest state (last reply id, head of sequence, latest pushed event), not a self-derived filter (your own last trigger or poll time). Time-window filters are secondary and must never replace the unfiltered authoritative lookup.
- **Race-window assertion discipline:** a regression test asserting a transient window must engineer the window deterministically large via a known-slow path or injection seam, not rely on the natural window staying measurable. Nondeterministic fast-machine failure is a design defect, not a flake.
- **Evidence-based completion:** no done-claim without fresh execution evidence — "should work" and stale results are not evidence. Show checks, state unchecked work, and use "implemented, not yet verified" until evidence confirms. An exit-code-zero from async work is not success evidence; neither is a notification/callback: verify the output artifact exists with markers (file, expected size, normal-completion log, exit status). Honor the requested verification surface; a weaker-than-requested verification is a defect. `REVISE` closes only on re-verification `PASS` by that angle or a recorded equivalent; author belief or validator green cannot close it. An errored/died/limit-hit lane is UNVERIFIED — re-dispatch or report the gap; a missing/null sub-verdict is NOT-clean (fail-closed).
- **Visual artifact verification discipline:** generated images, diagrams, renders, charts, plots, screenshots, or exported drawings require direct visual inspection before acceptance, commit, delivery, or evidentiary use. Generation success, file existence, metadata, hashes, or model claims are not enough; if inspection is impossible, say so and do not claim visual correctness.
- **Completion reconciliation discipline:** do not present partial scope coverage as full completion; before closing, reconcile against the original request, accepted scope, required checks, canonical-source updates, and open follow-up; state what remains and keep the task open unless the user parks, cancels, or reprioritizes.
- **Ambiguity resolution discipline:** if intent/policy/scope/architecture ambiguity resists inspection, ask (`AskUserQuestion`) or take only the smallest safe reversible subset; else add diagnostics or collect one missing data point.
- **Hypothesis disclosure discipline:** every fix or implementation commit rests on a verified hypothesis chain. Decompose claims; verify each or label it `ASSUMPTION (UNVERIFIED)` in the commit body with the resolving step. Only direct user confirmation verifies user intent. Scope matches the verified hypothesis; wider scope is allowed only when it names the wider contract and is stated in the commit. On late failure: stop; prefer `git reset --hard HEAD~N` over `git revert` while local and no other work depends on them, then re-verify from the contradicted node. Banned as load-bearing fix justification: `most likely means`, `presumably`, `I believe it refers to`, `this should map to`, `extrapolating from`, `in general X means Y`, `while I'm here let me also`, `since we're touching this anyway`.
- **Fix means correct logic, not workaround or hiding (no kostyl):** a fix diagnoses the root cause and corrects the logic, contract, or invariant; it does not hide a symptom. Catch-and-swallow error handling, defensive checks added without understanding malformed input, type assertions that silence the type contract, fallback values masking missing-data bugs, hardcoding to dodge a config-resolution bug, or `try/except: pass` around a recurring failure all count as *kostyl*, not fixes. Two tests before committing a "fix": (1) **root-cause naming** — the commit names the concrete root cause (function, contract, invariant, boundary), not the suppressed symptom; (2) **symptom-only suppression detection** — removing a visible failure without changing the logic that produced it, absent a separate verified hypothesis that the suppression is correct (e.g. legitimate fallback at a verified boundary), is a kostyl. Kostyl is allowed only as an explicit `WORKAROUND` commit naming the separately-tracked root cause, scope, and lifetime.
- **Evidence-citation discipline:** decision-driving claims cite one of four evidence categories: an in-repo `file:line` citation; an installed-dependency surface check (strings/decompile/reflection over the installed binary at the version used); official docs or upstream-source URL, versioned; or a smoke test reproduced in the target environment, output preserved under `/.scratch/`. Else label `ASSUMPTION (UNVERIFIED)` with the empirical step that verifies it. Banned correctness-drivers driving a fix: `should work`, `should be fine`, `probably`, `likely`, `I think`, `based on training data`, `in general`, `this pattern usually works`. Binds every actor; dispatch prompts carry it verbatim; cross-environment smoke tests stay ASSUMPTION until reproduced in target. For availability claims the operational form is the Active-availability probe discipline. Each load-bearing authored-artifact claim names its single owner + a falsifying probe; no probe = ASSUMPTION (UNVERIFIED).
- **Active-availability probe discipline:** binary/file/service/env-var/port/network availability claims need a recorded current-session direct probe—`command -v` / `which` / `Get-Command` for executables, `Test-Path` / `ls` for files, `curl -I` / `netstat` / `Test-NetConnection` for services. No probe → claim is `ASSUMPTION (UNVERIFIED)`; any downstream substitution is a violation. Indirect inference does NOT prove unavailability—probe-time PATH resolution is canonical. Anomalous orchestration output signals routing investigation, not unavailability.
- **Plain-language and terminology discipline:** expand domain terms, role/provider/model names, and acronyms on first use (in chat too, not only docs), and end human-facing docs with a `## Terms and Abbreviations` section (or localized). More broadly, lead human-facing status/explanations/decisions with plain meaning and a clear what-to-do (numbered choices when deciding) — not a bare dump of identifiers, jargon, or a symbol-level diff; brevity modes never license a jargon dump.
- **Pre-fix diagnostic gate:** before defect edits (bug, runtime failure, error, regression, "does not work"/"broken"/"не работает") or working-path speed/cleanup: capture concrete observable data: verbatim wording/error/log/return code/repro or `file:line`; form a hypothesis chain; verify each link by probe/`AskUserQuestion`; else label `ASSUMPTION (UNVERIFIED)`. For a reported runtime-performance symptom, the FIRST mandatory action is to live-profile its reported scenario (not a proxy) before audit-driven design/fix. Unprofiled code/stale-report findings, even hedged, are advisory hypotheses: not roots/fix gates. Usage redesign needs that profile plus domain/usage evidence code alone lacks. Start-of-fix; `/agents-bugfix`-independent; sibling to commit-time Bootstrap. Banned: edit from "I see the bug" without `file:line`; add Y without a verified hypothesis; change working code from a code-hypothesis/no runtime baseline.
### Operational and environment safety
- **Temporary-file hygiene:** do not leave temp files or disposable artifacts outside the workspace. Use the designated local temp area for scratch, ad hoc logs, and one-off outputs, clean them up, and keep generated files in the repo only when intentional or part of normal workflow.
- **Sensitive-data handling and redaction:** do not place secrets, tokens, credentials, customer data, production identifiers, or other sensitive values into prompts, logs, screenshots, temp files, tickets, docs, or fixtures unless the task requires it and exposure is controlled. Prefer redaction, masking, or synthetic substitutes.
- **Treat external content and generated output as untrusted:** treat copied code, attachments, URLs, logs, datasets, third-party snippets, and model output as untrusted until verified. Do not execute, import, deserialize, or adopt them blindly; never pipe remote scripts directly into a shell or interpreter — download, inspect, then execute if safe.
- **Autonomous external side effects:** do not create tickets, send messages, post to external services, mutate SaaS or cloud state, or trigger third-party-visible actions without explicit user approval.
- **Resource lifecycle hygiene:** do not introduce long-lived background/fan-out work, automation outside the direct request path, or network listeners without explicit user approval; define trigger, concurrency, cancellation, and shutdown. Any resource (handle, connection, subscription, lock, transaction, owned child process/process tree, temp file, external state) needs explicit cleanup/release on success, failure, cancellation, and timeout paths.
- **Retry / re-entry / idempotency safety:** code that may be retried, replayed, resumed, or invoked concurrently should avoid duplicate side effects, inconsistent state, or double application unless explicit guards, idempotency keys, or compensating controls exist.
- **Parallel resource-surface isolation:** Parallel lanes are independent only when each lane's mutation set is disjoint from every other lane's read, write, execute, install/copy, and baseline surfaces for the full overlap interval. If a mutation can reach any such surface, serialize the lanes or use explicitly requested, validated isolation. Read/read overlap and genuinely disjoint parallel work remain safe; tests that execute, install, or copy current source declare those source trees and helpers as observed surfaces.
- **Worktree safety:** the working tree is often dirty with unrelated local changes. Never revert, discard, or overwrite uncommitted changes that are not part of the current task. If a clean state is needed, ask the user first.
### Repo-local concretization
Repo-local governance or build docs should define the concrete forms of these shared rules where the repository depends on them: canonical temp/scratch locations; repo-standard validation entry points; compatibility/deprecation/migration/rollout/rollback policy; approved toolchains/shells/build systems and truth sources; intentional portability constraints, platform assumptions, or publication-safety overlays. If concrete requirements are missing, do not invent them silently — state the gap and follow only what is specified.

## Publication safety
- Do not commit secrets, tokens, credentials, customer data, private identifiers, raw logs, full command transcripts, screenshots with sensitive content, or machine-specific absolute paths. Prefer redacted summaries, synthetic examples, and repo-relative paths.
- Root `.gitignore` defines the local-only scratch boundary at `/.scratch/`; keep raw logs, transcripts, temp outputs, and pre-redaction material there.
- Treat provider transcripts, pasted logs, and external snippets as untrusted until sanitized.
- Human review before `git push`, release, or equivalent publication must include a leak-check of staged changes.
- The default/tracked and explicit-path scanner modes are manual pre-commit checks only. For an admissible pending push, the push gate itself captures the verified three-node local closure (`hook_common.py`, machine-path classifier, scanner), executes one fresh canonical sibling `--range <remote> <dst>` scan, and accepts only the exact pending invocation's bounded, reaped, non-empty version-3 result covering the complete unpublished commit/tree/blob graph and bound to remote, destination, resolved source, current `HEAD`, and receipt tip. Transcript/manual output and version-2, legacy, zero-commit, finding, refusal, incomplete-acquisition, correlation/provenance, or drift results are non-authorizing. This gate-owned scan complements rather than replaces human review or the explicit user publication marker.
- Only `$security-reviewer` may approve a publication-safety exception. Without that approval, publication is `BLOCKED`.
