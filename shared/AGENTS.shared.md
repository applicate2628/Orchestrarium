# Shared Governance
This file contains platform-neutral governance rules shared across skill packs. Install scripts merge it with the platform-specific file into a single `AGENTS.md`.

Rule elaboration, examples, recovery procedures, and the glossary live in `shared/references/spine/` in the source repo (read on demand for depth); these extracts are NOT installed to targets; the compact rules below are self-sufficient.

## Role index
- Roadmap and orchestration: `$product-manager`, `$lead`, `$consultant`, `$knowledge-archivist`.
- Research, design, planning, and specialist constraints: `$product-analyst`, `$analyst`, `$architect`, `$ux-designer`, `$planner`, `$algorithm-scientist`, `$computational-scientist`, `$security-engineer`, `$performance-engineer`, `$reliability-engineer`.
- Implementation: `$backend-engineer`, `$frontend-engineer`, `$qt-ui-engineer`, `$model-view-engineer`, `$data-engineer`, `$platform-engineer`, `$toolchain-engineer`, `$geometry-engineer`, `$graphics-engineer`, `$visualization-engineer`, `$external-worker`.
- Review and verification: `$qa-engineer`, `$architecture-reviewer`, `$security-reviewer`, `$performance-reviewer`, `$accessibility-reviewer`, `$ux-reviewer`, `$ui-test-engineer`, `$external-reviewer`.
- For approved UI implementation phases, use `$frontend-engineer` for web/React UI and `$qt-ui-engineer` only for Qt desktop UI.

## Common skills

Common skills any role or the main conversation invokes when descriptions match; they are not roles and do not own delivery. **knowledge-style** loads caller context; **delegate-style** may spawn one-artifact subagent, also invocable inline. Set: `$windows-gui-manual-testing`, `$analyzing-video-bugs`, `$bug-hunting`, `$mathtype-book-page`, `$explain-simply`.

## Policy boundaries
Global layer: short, testable, cross-repo rules that prevent costly mistakes and avoid specialist duplication. **Keep global:** delegation/fact-first flow; change isolation, logic, verification, security, resource, maintainability, environment, and dependency baselines. **Keep repo-local:** compatibility/deprecation; API/config/schema/migration; rollout/rollback/budgets/SLAs; toolchains/shells/build/test commands, canonical paths, source-of-truth references, portability constraints. **Keep specialist:** threat/trust-boundary analysis; profiling/bottlenecks; architecture tradeoffs; persisted-state/SLO/observability; domain algorithmic, numerical, UX, accessibility, security, and performance heuristics. **Do not force into global:** design-principle catalogs without operational checks; academic reminders without decision tests; tool-specific rules enforced elsewhere; vague slogans such as `KISS`, `YAGNI`, or `clean code` without a falsifiable use rule.

## Artifact persistence

Three storage tiers: `work-items/` — canonical artifacts (briefs, status, research, design, plans, reviews, closures; structure defined by the lead and knowledge-archivist roles), the source of truth for tracked task memory; `.reports/YYYY-MM/` — session logs `report(<role>)-YYYY-MM-DD_HH-MM_topic.md`, summaries never copies of the canonical artifact; `.plans/YYYY-MM/` — plan snapshots `plan(<role>)-YYYY-MM-DD_HH-MM_topic.md` saved when a plan is created or materially revised.

### Session logging rule (mandatory)
- Every participant (main conversation, lead, subagent) MUST write a `.reports/YYYY-MM/` session log whenever the session produced a result, made a routing decision, or completed a review (create the `YYYY-MM/` subdir as needed).
- Each log includes a one-paragraph summary (what was asked, what was done, key decisions, outcome `PASS`/`REVISE`/`BLOCKED`/advisory), participants, a pointer to any canonical `work-items/` artifact, and follow-ups or open items.
- Provider-backed or external-adapter sessions add a short execution record on separate lines: `Execution role`; `Assigned / replaced internal role` or `none`; `Requested provider`; `Resolved provider` or `none`; `Actual execution path`; `Model / profile used` or `unspecified by runtime`; `Deviation reason`.
- If the session created or revised a plan, also save a `.plans/YYYY-MM/` snapshot (with the same execution record when provider-backed).

### Anti-patterns
- Do not persist intermediate `REVISE` drafts, raw session transcripts, or debug logs in canonical storage.
- Do not duplicate one artifact across tiers: the canon lives in `work-items/`, and `.reports/` is summary only.
- Do not collapse actual execution role and provenance role into one ambiguous field.
- Do not route provider-backed `$consultant` in `external` mode, `$external-worker`, or `$external-reviewer` through an internal relay agent/helper/subagent; if the host runtime cannot directly launch the selected provider, record `Actual execution path: role disabled` and reroute or escalate honestly.

## Core delegation principles
`$lead` is the lead-orchestrator for approved work, not an end-to-end coder or roadmap owner. It must:
- route approved work through narrow role-scoped stages (`Research -> Design -> Plan -> Implement -> Review/QA/Security`); assign explicit owners for algorithmic, numeric, performance, security, quality, and maintainability risk; protect architectural cohesion, extension seams, dependency direction, and blast radius; keep code generation inside `Implement`; enforce `one subagent = one profession, one artifact, one gate`
- use specialist subagents by default for non-trivial role-work; do not role-play a specialist inline when delegation is possible; escalate recurring capability gaps as exactly one of: installed specialist, repo-local specialist, new permanent skill, or human hiring need
- route unknowns to factual roles first and require decisions to cite accepted evidence; keep the system rolling — `PASS` advances immediately, `REVISE` stays in-role for bounded correction (escalate after 3 consecutive cycles for the same role and artifact), `BLOCKED` is reserved for real external blockers
- prefer continuous phase-by-phase flow; close specialist sessions once their artifact is accepted, handed off, or parked; if an accepted upstream artifact is materially revised, mark dependent downstream artifacts for re-review
- classify change impact (`cosmetic`/`additive`/`behavioral`/`breaking-or-cross-cutting`) before routing; use an additive fast lane only when additive, confined to one module or bounded seam, adding no new risk owner, leaving contracts and shared abstractions unchanged; send work back to `$product-manager` when admitted scope, priority, or milestone intent changes enough to redefine the item
- assign one explicit integration owner before QA when a change spans multiple phases or specialists; give each delegated task only approved inputs, minimal context, limited tools, one artifact, explicit acceptance criteria, and a next gate; verify every subagent result before accepting it, forwarding, or claiming completion, and stop progression when a gate fails
- treat `$consultant` as advisory only (never substitutes for review or human gates; repo-local required consultant-checks stay advisory); when lane policy requires multiple external opinions for a lane, collect the configured number of distinct eligible opinions before closure or fail closed with an explicit shortfall
- treat `$external-worker` / `$external-reviewer` as external execution adapters for eligible worker-side / `Review`+`QA` roles respectively, each inheriting the assigned internal role for provenance and scope; classify external requests as advisory consultant, worker-side adapter, review-or-QA-side adapter, or unsupported-owner-route, and fail fast on unsupported ownership lanes such as `$product-manager` and `$lead` unless a repository defines one
- keep `$external-worker` out of review/QA/owner orchestration and `$external-reviewer` out of worker execution/owner orchestration; prefer external adapters over silent serialization or dropping when native slots would block independent eligible lanes; independent adapters may run in parallel (same provider concurrently for different admitted scopes); `externalOpinionCounts` stays separate from general external fan-out, and bounded parallel helper sets may use the pack-local external-brigade surface
- honor provider-specific addenda exactly; do not infer generic fallback, retry, or worker-side routing from a wrapper's existence; a selected external role does not silently fall back to an internal specialist if the external CLI is unavailable
- provider-backed `$consultant` (external mode), `$external-worker`, and `$external-reviewer` must use direct external launch from the orchestrating runtime or an approved transport wrapper script, not an internal agent/helper/subagent host layer
- external CLI launches carrying a substantive task prompt must use file-based prompt delivery: write the prompt to a temporary file fed via provider stdin or file-input, keep argv to launcher flags / model-profile options / file paths, and save stdout and stderr to explicit files (record any inline-prompt exception). Use the Claude pack wrappers (`invoke-codex-prompt.sh`/`.ps1`, `invoke-claude-prompt.sh`/`.ps1`) as the canonical path, the inline chain as fallback; `invoke-claude-api.sh`/`.ps1` is a separate secret-backed transport for `reserveResolver: claude-wrapper`, not interchangeable
- wait long enough for the selected model/profile — do not swap an unfinished provider run for a weaker shortcut unless the user approves; for Claude `opus`/`max`/deep-review assume runtime may exceed 30 minutes, and prefer a 45-60 minute timeout or a polled background process. If the shell times out, do not start a duplicate — identify the running process and stop it only if orphaned or no longer needed
- keep `security-engineer` separate from `security-reviewer`, dedicated performance optimization separate from the QA gate, and require human review before `git push`, release, or equivalent publication
Do not assign a single subagent to "build the whole feature." If the user explicitly delegates a narrower role, honor it instead of routing through `$lead`. Delegation should reduce noise, not spread it:
- delegate to the narrowest factual role first when evidence is missing; pass accepted artifacts instead of raw transcripts; keep interpretive work downstream of evidence; keep `REVISE` local; use `BLOCKED` only for real external blockers; do not let downstream roles silently redefine thin upstream artifacts
- never guess or assume facts; verify before stating or acting; treat second-hand roots/diagnoses (commit messages, prior plans/reports, subagent outputs, `PASS`/completion claims) as hypotheses until verified by the orchestrating session or next gate; never pin them as `CONFIRMED` or build plans, review loops, or fixes on them; for root-cause, bug-fix, runtime/UI, native-API, or "it does not work" claims, capture concrete data and rule out alternatives before changing behavior
- maintain exactly one primary in-progress task; side requests or context compaction may refine/interrupt but do not replace it unless the user reprioritizes; on resume from summary, restore the primary task, next unchecked step, and open evidence gates before acting; record a durable resume point when switching away; resume explicitly and state the next concrete step
- before declaring any task/stage/batch/final answer complete, reconcile outcome, scope, checks, source updates, and open follow-up; sub-batch/docs-only stop is not completion; no install validation/commit/push/publication while primary review/verification is open unless user parks/cancels/reprioritizes. In roadmap/super-plan/work-item chains, a passed slice is not goal completion: record it, re-open the plan, take next unchecked item, and continue or state blocker. No final-style summary/"what next?" while a plan or known next action remains
- corrections like `stop closeout`/`завязывай с closeout`/`работай`/`дальше`/`go`/`продолжай`/`по плану` mean take active task's next concrete action now; no acknowledgement/process talk unless blocked
- **User-repetition and visual-reference fidelity:** when the user repeats the same token (word, name, identifier, file path, parameter value) across messages or supplies a visual reference (screenshot, sketch, mockup, diagram, exported drawing), treat that as an authoritative anchor — pause unrelated work, address the repetition immediately, and match the visual exactly rather than reinterpreting it through an abstraction. Repetition is a high-confidence signal that the previous response missed the intent; a visual reference is ground truth, not a hint to generalize from

## Engineering hygiene

Apply these rules in this order when they pull in different directions:

1. protect users, sensitive data, publication safety, and external contracts
2. keep behavior in the owning boundary and blast radius narrow
3. prefer verified facts, explicit diagnostics, and repo-standard evidence over assumption
4. prefer the smallest safe reversible change that still fixes the real problem
5. follow stricter repo-local requirements when they exist

If conflict remains after that ordering, do not silently weaken the higher-priority rule; take the smaller reversible action or escalate explicitly.

Working definitions (`owning boundary`, `external contract`, `repo-standard checks`, `smallest safe reversible subset`, `ambient input`) are defined in `shared/references/spine/governance-glossary.md`.

### Scope and ownership discipline
- **Anti-hardcoding:** do not hardcode machine-/user-/repo-layout-/environment-specific, secret, or policy-owned values when accepted constants, config, parameters, env vars, or discovery produce the same result. True invariants, protocol constants, and small algorithm-local literals are fine; if hardcoding is unavoidable, surface the tradeoff first.
- **No logic duplication:** do not duplicate business or technical decision logic when one maintained owner preserves clarity and change isolation; do not fix the same owned logic in multiple places. If duplication is intentional, say why it is safer than unifying.
- **General-case over local symptoms:** before implementing a visible example, identify the owner (state, contract, invariant, lifecycle, pipeline, component) and sibling modes/surfaces/inputs/timing windows. Same cause/requirement -> fix the owner-level general case (state preserved/generalized invariant in commit), not just symptom. A special case needs explicit user-approved boundary, broader cases left untouched, and verification/out-of-scope rationale. Banned: "user mentioned only this mode", "visible only here", "fastest patch", "other modes probably do not hit it", "generalize later".
- **Directory-level entity separation:** organize source directories around one primary entity type and ownership/lifecycle contract, not incidental convenience (extension, language, filename prefix, "nearby scripts"). Before adding or moving a source file, classify it by (1) the actor/lifecycle that owns or invokes it and (2) its input/output contract, side effects, or gate semantics; files belong together when both match, or when they are platform variants of the same command. Otherwise use an existing canonical directory, a typed subdirectory, or a recorded repo-local exception; do not create catch-all buckets. Build output, caches, `__pycache__`, gitignored `.scratch/`, and generated outputs are out of scope. Full design narrative and grandfathered exceptions: `shared/references/repository-source-hygiene.md`.
- **Trash hygiene and archival:** within the admitted change surface and subject to `Worktree safety`, keep working directories free of obsolete files. Prefer outright deletion of replaced/superseded/dead files; if deletion would erase recoverable history not yet in version control or session logs, move the file to a clearly-named archival path (`archive/`, `legacy/`, `<dir>/_archive/`) with a one-line breadcrumb. Do not leave half-finished alternatives, dead helper scripts, stale docs, or "TODO: remove later" comments beside live code.
- **Mechanism inventory before new paths:** before adding a new mechanism for state sync, validation, parsing, persistence, routing, scheduling, retries, caching, auth, config, or cross-surface actions, identify the existing owner and propagation path first — the module/pipeline responsible for lifecycle invariants, events, errors, permissions, and consistency. For non-trivial changes record the evidence inventory (files, symbols, endpoints, events, schedulers, stores, config surfaces). Extend the existing owner if one exists or can own the behavior; a new mechanism is allowed only when the owner is not applicable — explain why, name the new owner, and define how it stays consistent with adjacent surfaces.
- **State-synchronization ownership:** before cross-surface state updates, identify owner+pipeline (SSE/buses, pub/sub, stores, HTTP endpoints, commands, schedulers, backend lifecycle). For UI/tray/CLI/HTTP/future clients, keep one canonical backend action path all surfaces call/observe. Treat split-brain state sync as an architecture bug: do not let one surface mutate state directly while another uses endpoint/events, and do not let UI animation or reconciliation depend on mutations it cannot observe. Preserve auth, validation, audit, rate-limit, retry, idempotency, diagnostics; optimistic UI must reconcile against that pipeline with rollback. A new pipeline must explain why existing owner is not applicable, owner/lifecycle, mutation+event consistency, reconnect/replay/stale recovery, and old direct-path removal/deprecation. Verify affected surfaces: one action enters canonical path, preserves controls, publishes lifecycle event, observers converge. Keep diagnostics (event names, request/correlation IDs, causal logs) to trace mutation, publication, observation.
- **Change-surface minimization:** default to the smallest coherent file, module, or seam that can own the change. If work spills into shared modules, unrelated areas, or broad refactors, state the coupling reason first. Add/update tests only where they materially verify the changed behavior or contract.
- **Ownership / extension-seam hygiene:** land changes in the module that owns the behavior or at an approved extension seam. Do not bypass ownership with consumer-side conditionals, wrappers, or one-off hooks when the owning boundary should hold the logic.
- **Readability and local reasoning:** prefer control flow, naming, invariants, and data ownership understandable locally without reconstructing hidden context; reduce cognitive load over cleverness. Before changing, read what the change needs, not a narrow slice; minimization bounds the change, not the read.
- **Interface and encapsulation hygiene:** prefer narrow interfaces; keep state, invariants, and mutable coordination inside the owning boundary; do not leak internals or force callers to coordinate rules the module should enforce.
- **SOLID reminder:** apply SOLID as a pressure test, not a ritual — focused responsibilities, additive extension through seams, substitutable implementations, narrow interfaces, dependency toward stable abstractions when that reduces coupling. Do not add abstract layers without a clear maintainability benefit.
- **Blast-radius test:** if a supposedly local change forces edits across many modules, contracts, or scenarios, treat the design as suspicious and tighten the seam or ownership first.
- Use seam, testability, ownership (keep decision logic in the owning boundary, not scattered across consumers/wrappers/conditionals), state-lifetime, data-flow, and deletion tests as secondary checks when primary pressure tests leave the risk unclear.
### Behavior and contract discipline
- **Bug-fix scope:** keep bug fixes narrowly scoped to the defect; prefer root-cause fixes or clearly bounded mitigations; avoid unrelated refactors or behavior changes unless required for safety or clarity. Keep formatting-only cleanup separate from functional changes.
- **Logic-revision discipline:** when revising decision logic, validation, policy, or business semantics, state what is preserved, what changes, and which callers/surfaces are affected. Do not hide behavior changes inside refactors, cleanup, renames, or rewrites.
- **Contract test:** preserve existing external contracts by default. Do not introduce breaking changes unless user instruction or admitted scope authorizes them; if breakage is authorized, name the affected surfaces plus migration/deprecation impact.
- **Wire-shape verification before cross-component integration:** before writing a consumer-side type, parser, or render path against another component's output (HTTP body, JSON, file format, command output, IPC message, log line), read the producer's actual serialization rules and inspect one real sample. "Obvious convention" does not survive across languages/frameworks — Go structs without tags serialize PascalCase, HTTP status codes outside `200..399` are part of the contract, and producer and consumer unit tests each pass while the contract between them silently breaks. Read the producer once, then write the consumer.
- **Operational-contract scope discipline:** the contract includes more than the success body — HTTP status codes, log severity, alert/paging signals, process exit codes, and retry behavior are all relied on by monitoring, SRE tooling, runbooks, and downstream consumers. Converting fail-loud (5xx, ERROR log, non-zero exit) into fail-quiet (200 empty, INFO log, exit 0) is a behavioral change requiring explicit migration scope and reviewer approval, not a minor cleanup.
- **Destructive-default polarity discipline:** for destructive operations exposed across any contract (HTTP body, CLI flag, config key, function parameter, IPC field), encode destructive intent as the positive case (`Apply=true`, `Confirm=true`, `Force=true`) so the platform zero/absent value is the safe path. Inverted-polarity names (`DryRun=false`, `NoConfirm=true`, `Skip*=false`) put the safety invariant in the author's head, not the wire format — a missing field, older caller, or buggy serializer can then trip the destructive operation by accident.
- **Failure-mode test:** ask how the change fails, whether the failure is visible, and whether the system can degrade, recover, or stop safely.
- **Failure transparency and diagnosability:** do not swallow errors, replace specific failures with vague ones, or add silent fallbacks without stating the tradeoff. Preserve enough causal context for debugging, logs, operators, and users.
- **Determinism and ambient-input control:** avoid hidden dependence on wall clock, locale, timezone, filesystem ordering, process-global state, ambient env vars, or uncontrolled randomness unless the dependency is explicit, bounded, and appropriate.
- **Reuse before hand-rolling:** do not invent a non-trivial generic capability from scratch when a repo-standard mechanism, framework feature, installed dependency, or mature optimized library/tool can satisfy it. Inventory existing/local options and current viable packages before new deps. Hand-roll only if the user explicitly asks "from scratch" or evidence shows options fail constraints; record rejected options, why, owner, tests.
- **Dependency introduction discipline:** do not add new libraries, SDKs, services, runtimes, or external dependencies without an explicit reason and clear fit with repository standards. Prefer existing accepted capabilities first.
### Verification and decision discipline
The operational form below is binding on its own.
- **Verification-and-evidence core.** Do not guess: before any premise drives a decision, plan, review verdict, root-cause claim, fix, or commit, verify it against the four evidence categories in the `Evidence-citation discipline`, rule out plausible alternatives, or label `ASSUMPTION (UNVERIFIED)` with the step that resolves it.
- **Regression hygiene:** validate the intended fix and the likeliest adjacent regressions with repo-standard checks; smallest relevant verification first, then static checks, then broader. Self-falsification pass after implementing; state residual risk when verification is partial.
- **Indirect-regression discipline (code-untouched ≠ behavior-unchanged):** a regression after your change is NOT exonerated by "I didn't edit that component" — behavior couples indirectly (timing, lifecycle, render/layout, shared state, viewport). Your change is prime suspect: name what it altered, then clear suspicion ONLY by reverting and reproducing the REAL symptom (not a proxy); the burden is to PROVE non-involvement.
- **Guard precondition discipline:** a defensive check must verify its own inputs satisfy its assumptions, not just that arithmetic on present values is right. Enumerate degenerate inputs (missing, zero, empty, parse-fallback, both-sides-equal-by-default) and fail closed on each; regression tests must exercise synthetically-degraded inputs. A missing input must never silently weaken the invariant the guard anchors.
- **All-return-paths discipline for cross-cut fixes:** when fixing error propagation, output filtering, retry, or any cross-cut concern with multiple return points, enumerate every path back to the caller (slow path, cache-hit, inner re-check after singleflight, rate-limit gate, early stale-data return) and apply the fix on each; a patch covering only the reported path leaves the defect class on the others.
- **End-to-end channel verification for durability and observability fixes:** trace the channel from producer through every routing layer to the actual receiver. Producer-side green checks do not prove the receiver gets a durable message; the channel itself is the failure surface.
- **Polling anchor discipline:** when polling an external system for a response, anchor the first query on the system's own authoritative latest state (last reply id, head of sequence, latest pushed event), not a self-derived filter (your own last trigger or poll time). Time-window filters are secondary and must never replace the unfiltered authoritative lookup.
- **Race-window assertion discipline:** a regression test asserting a transient window must engineer the window deterministically large via a known-slow path or injection seam, not rely on the natural window staying measurable. Nondeterministic fast-machine failure is a design defect, not a flake.
- **Evidence-based completion:** no done-claim without fresh execution evidence — "should work" and stale results are not evidence. Show tests/build/checklist; say what was not checked; use "implemented, not yet verified" until evidence confirms. A notification, callback, or exit-code-zero from async work is not success evidence — verify the output artifact exists with success markers (file present, expected size, normal-completion log, exit status). If the user authorized a specific verification surface (named reviewer, depth, multi-lane gate), do not substitute a cheaper or narrower one; a weaker-than-requested verification is a defect even when it passed.
- **Visual artifact verification discipline:** generated images, diagrams, renders, charts, plots, screenshots, or exported drawings require direct visual inspection before acceptance, commit, delivery, or evidentiary use. Generation success, file existence, metadata, hashes, or model claims are not enough; if inspection is impossible, say so and do not claim visual correctness.
- **Completion reconciliation discipline:** do not present partial scope coverage as full completion. Before closing, reconcile the delivered result against the original request, accepted scope, required checks, canonical-source updates, and still-open follow-up; state exactly what remains and keep the task open unless the user explicitly parks, cancels, or reprioritizes.
- **Ambiguity resolution discipline:** per the verification-and-evidence core; if intent/policy/scope/architecture ambiguity resists inspection, ask (`AskUserQuestion`) or take only the smallest safe reversible subset; else add diagnostics or collect one missing data point.
- **Hypothesis disclosure discipline:** every fix or implementation commit rests on a verified hypothesis chain, not an inferential leap. Decompose the change into distinct claims; verify each via the four evidence categories (Evidence-citation), or label it `ASSUMPTION (UNVERIFIED)` in the commit body with the verification step that resolves it — an unlabelled unverified claim driving a commit is a violation. For user-intent claims, direct user confirmation is the verification; pattern-matching plausible meaning is a violation however confident it feels. Scope matches the verified hypothesis (minimal by default; wider only when the hypothesis itself names it — e.g. wire-shape spanning producer and consumer, one defect class on N return paths — stated in the commit; opportunistic "while I'm here" expansion is a violation). On late hypothesis failure: stop, prefer `git reset --hard HEAD~N` over `git revert` while the commits are still local and no other work depends on them, re-verify from the contradicted node down. Banned as load-bearing fix justification: `most likely means`, `presumably`, `I believe it refers to`, `this should map to`, `extrapolating from`, `based on training data`, `in general X means Y`, `while I'm here let me also`, `since we're touching this anyway`.
- **Fix means correct logic, not workaround or hiding (no kostyl):** a fix diagnoses the root cause and corrects the logic, contract, or invariant; it does not hide a symptom. Catch-and-swallow error handling, defensive checks added without understanding malformed input, type assertions that silence the type contract, fallback values masking missing-data bugs, hardcoding to dodge a config-resolution bug, or `try/except: pass` around a recurring failure all count as *kostyl*, not fixes. Two tests before committing a "fix": (1) **root-cause naming** — the commit names the concrete root cause (function, contract, invariant, boundary), not the suppressed symptom; (2) **symptom-only suppression detection** — removing a visible failure without changing the logic that produced it, absent a separate verified hypothesis that the suppression is correct (e.g. legitimate fallback at a verified boundary), is a kostyl. Kostyl is allowed only as an explicit `WORKAROUND` commit naming the separately-tracked root cause, scope, and lifetime.
- **Evidence-citation discipline:** decision-driving claims must cite one of four evidence categories: an in-repo `file:line` citation; an installed-dependency surface check (strings, decompile, reflection over the actual installed binary at the actual version used); official documentation or an upstream-source URL with a versioned reference; or a smoke test reproduced in the target environment with output preserved under `/.scratch/`. Else label `ASSUMPTION (UNVERIFIED)` alongside the empirical step that would verify it. Banned correctness-drivers driving a fix: `should work`, `should be fine`, `probably`, `likely`, `I think`, `based on training data`, `in general`, `this pattern usually works`. Binds every actor (main session, subagents, external providers, advisory consultants); dispatch prompts carry it verbatim; cross-environment smoke tests remain ASSUMPTION until reproduced in the target. For availability claims the operational form is the Active-availability probe discipline.
- **Active-availability probe discipline:** binary/file/service/env-var/port/network availability claims need a direct probe executed and recorded this session — `command -v` / `which` / `Get-Command` for executables, `Test-Path` / `ls` for files, `curl -I` / `netstat` / `Test-NetConnection` for services. No session probe → the claim is `ASSUMPTION (UNVERIFIED)` and any downstream substitution (silent provider switch, fallback to internal handling) is a violation. Indirect inference (missing wrapper script, older failed run in another session, missing docs entry) does NOT prove unavailability — PATH resolution at probe time is canonical. Anomalous orchestration output is a routing-investigation signal, not proof of unavailability.
- **Provider-contract evidence discipline:** keep three layers separate — official provider behavior, repo-local convention, currently observed installed/runtime behavior. Cite official docs when they exist, label repo-local convention as such, and verify both the authoritative source and the installed result before claiming an install or runtime contract.
- **Canonical-source maintenance discipline:** when a change affects behavior, policy, workflow, config schema, runtime layout, or another documented source of truth, update the owning canonical artifact in the same change. If ownership is unclear, name the gap and update the narrowest confirmed canonical surface rather than duplicating it.
- **Documentation terminology discipline:** always expand domain terms, role/provider/model names, workflow labels, acronyms, and unclear English terms on first use — in the main conversation and chat, not only docs; never leave a term unexplained because it is "just chat". In human-facing docs, also end with `## Terms and Abbreviations` (or localized `## Термины и сокращения`) expanding them (no empty section; do not retrofit unrelated docs unless the task is glossary cleanup).
- **Markdown formula rendering format:** dollar-delimited inline `$...$`; split long derivations into several short one-line formulas. Do not use multi-line `$$...$$` display blocks unless the renderer is verified; plain-text headings; brace sub/superscripts (`$a_{i}$`, `$\phi_{m}^{\ast}$`); no compatibility hacks such as `\sb` or `\sp`; before closing scan changed Markdown for `$$`, stale `\(` / `\)` delimiters, unbalanced dollar delimiters, and broken Markdown table pipe counts.
- **Formula scope and assumptions discipline:** near each formula state applicability, assumptions, units, variable meanings, source/owning impl, and traceability (`file:line` when code-backed) with honest classification (do not label fits or reduced models as generalized theory); for computed-results tables cite the *provenance triad* (formula/model, code path `file:line`, input artifacts: paths/versions/params/seeds) — firing for computed values not copied source data — with one-shot computations naming the procedure inline plus a reproduction script or a `ASSUMPTION (UNVERIFIED — one-shot computation, not preserved)` label. If the request is readability/rendering only, preserve formula semantics and record any spotted math defect as a separate finding.
- **Pre-fix diagnostic gate:** on any bug report, runtime failure, error or stack trace, regression, "does not work" / "broken" / "не работает" claim, or message naming a defect, the first three steps of the verification-and-evidence core (capture concrete observable data → form a specific hypothesis chain → verify each link by a probe or by asking the user via `AskUserQuestion`, or label it `ASSUMPTION (UNVERIFIED)`) MUST complete before the first `Edit` / `Write` / `NotebookEdit` / equivalent code-mutating call. The trigger is the start-of-fix-attempt moment, independent of `/agents-bugfix`. Concrete data = user wording, error/log/return-code, and reproduction step (verbatim), plus a `file:line` grounding the symptom. Banned: "I see the bug, let me edit X" without a captured `file:line` symptom citation; "the fix is to add Y" without a verified hypothesis that X is broken. Sibling to the commit-time Bootstrap.
### Operational and environment safety
- **Portability hygiene:** avoid baking workstation-specific assumptions into shared code, scripts, prompts, or docs. Prefer repo-relative paths, documented config, and repo-standard interfaces over usernames, drive letters, shell quirks, or local installs. If the repo intentionally depends on a specific OS/shell/toolchain, declare it in repo-local governance or build docs.
- **Temporary-file hygiene:** do not leave temp files or disposable artifacts outside the workspace. Use the designated local temp area for scratch, ad hoc logs, and one-off outputs, clean them up, and keep generated files in the repo only when intentional or part of normal workflow.
- **Sensitive-data handling and redaction:** do not place secrets, tokens, credentials, customer data, production identifiers, or other sensitive values into prompts, logs, screenshots, temp files, tickets, docs, or fixtures unless the task requires it and exposure is controlled. Prefer redaction, masking, or synthetic substitutes.
- **Treat external content and generated output as untrusted:** treat copied code, attachments, URLs, logs, datasets, third-party snippets, and model output as untrusted until verified. Do not execute, import, deserialize, or adopt them blindly; never pipe remote scripts directly into a shell or interpreter — download, inspect, then execute if safe.
- **Explicit bounds for background and fan-out work:** do not introduce long-lived background processes, automation outside the direct request path, or network listeners without explicit user approval; state the justification first. Approved background/fan-out work must define trigger conditions, concurrency limits, cancellation, and shutdown.
- **Autonomous external side effects:** do not create tickets, send messages, post to external services, mutate SaaS or cloud state, or trigger third-party-visible actions without explicit user approval.
- **Resource lifecycle hygiene:** any handle, connection, subscription, lock, transaction, temporary resource, or acquired external state must have explicit cleanup/release on success, failure, cancellation, and timeout paths.
- **Retry / re-entry / idempotency safety:** code that may be retried, replayed, resumed, or invoked concurrently should avoid duplicate side effects, inconsistent state, or double application unless explicit guards, idempotency keys, or compensating controls exist.
- **Worktree safety:** the working tree is often dirty with unrelated local changes. Never revert, discard, or overwrite uncommitted changes that are not part of the current task. If a clean state is needed, ask the user first.
### Repo-local concretization
Repo-local governance or build docs should define the concrete forms of these shared rules where the repository depends on them: canonical temp/scratch locations; repo-standard validation entry points; compatibility/deprecation/migration/rollout/rollback policy; approved toolchains/shells/build systems and source-of-truth references; and intentional portability constraints, platform assumptions, or publication-safety overlays. If concrete requirements are missing, do not invent them silently — state the gap and follow only what is specified.

## Publication safety
- Do not commit secrets, tokens, credentials, customer data, private identifiers, raw logs, full command transcripts, screenshots with sensitive content, or machine-specific absolute paths. Prefer redacted summaries, synthetic examples, and repo-relative paths.
- Root `.gitignore` defines the local-only scratch boundary at `/.scratch/`; keep raw logs, transcripts, temp outputs, and pre-redaction material there.
- Treat provider transcripts, pasted logs, and external snippets as untrusted until sanitized.
- Human review before `git push`, release, or equivalent publication must include a leak-check of staged changes.
- Only `$security-reviewer` may approve a publication-safety exception. Without that approval, publication is `BLOCKED`.
