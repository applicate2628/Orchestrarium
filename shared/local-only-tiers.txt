# Canonical list of local-only runtime storage tiers (the single owner).
# Each installer ensures these are present in the target repo's .gitignore, because
# session logs, plan snapshots, and repo-local task memory are local-only output.
# Validator-only: tests/test_local_only_gitignore_tiers.py asserts every installer
# (install-{claude,codex,gemini,qwen}.{sh,ps1}) carries exactly this set. The
# installers keep the list inline for readability; this file is the drift owner.
#
# Declining a tier: an operator who deliberately wants a tier tracked in git
# (e.g. keeping work-items/ under version control on purpose) can leave the
# exact sentinel comment `# orchestrarium:local-only-tier-declined:<entry>`
# (e.g. `# orchestrarium:local-only-tier-declined:/work-items/`) in .gitignore
# in place of that tier's own line. The writer honors it on every reinstall and
# never re-appends the declined entry. Without this marker, whole-line
# presence matching cannot distinguish "never configured" from "considered and
# removed" (see
# work-items/bugs/2026-07-25-tier-writer-silently-reverts-considered-decline.md).
#
# git's OWN negation syntax is ALSO sticky (not just the sentinel above): a
# `!entry` line -- however it is spelled, and whether or not a companion
# positive pattern for the same tier exists anywhere else in the file --
# is honored and never overridden by an end-of-file append. Negation
# detection is DELEGATED to real `git check-ignore` (not a fixed spelling
# list): three successive rounds of widening a literal enumeration (two
# forms, then four) each missed real spellings git itself honors -- glob
# forms (`!**/work-items/`), character classes (`!/work-item[s]`),
# single-char wildcards (`!/work-item?`). Delegation itself then shipped with
# a narrower but more dangerous gap: a whole-file before/after-stripping
# differential cannot tell a BARE, unpaired negation (no companion positive
# pattern) apart from a genuinely missing tier, since both are un-ignored
# either way -- appending in that case added the very pattern the operator
# had just negated, flipping git's real verdict to the OPPOSITE of what was
# written. The writer now tests EACH `!`-prefixed line's own stripped
# pattern in ISOLATION against the tier, in an isolated throwaway repo (never
# the operator's real .gitignore or repo, and NEUTRALIZED against the
# operator's ENTIRE ambient git environment -- not just the specific vectors
# found so far, but the WHOLE git-documented class of repository-location
# and configuration-location environment variables, cleared in one place for
# the duration of the probe: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`,
# `GIT_NAMESPACE`, `GIT_CEILING_DIRECTORIES`,
# `GIT_DISCOVERY_ACROSS_FILESYSTEM`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`,
# `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_SYSTEM`, and
# `GIT_CONFIG_COUNT`, on top of `GIT_CONFIG_NOSYSTEM` + a nonexistent
# `GIT_CONFIG_GLOBAL` + `git init --template=<nonexistent>`. A global
# `core.excludesFile` or `init.templateDir` covering the tier, or an ambient
# `GIT_WORK_TREE` (alone, or paired with `GIT_DIR`) pointing at a different
# repository entirely, or a `GIT_CONFIG_COUNT`-injected config value, would
# otherwise each independently make the writer silently decide "already
# ignored" for a project whose own .gitignore says nothing about it --
# confirmed this session on both bash and PowerShell (GIT_WORK_TREE alone
# redirects both the working tree and git-dir discovery, so a
# working-tree-relative source like `.gitignore` leaks; GIT_DIR alone
# redirects only git-dir discovery, so a git-dir-relative source like
# `$GIT_DIR/info/exclude` leaks instead -- different channels, both real,
# both closed by clearing both variables), and that piecemeal fixes for
# named vectors (round 6 closed two, round 7 found a third the same way,
# round 8 found a fourth that was not an environment variable at all --
# core.excludesFile's own default-PATH fallback, which fires precisely when
# GIT_CONFIG_GLOBAL=<nonexistent> leaves it unset, and is closed instead by
# setting core.excludesFile EXPLICITLY on the throwaway repo) guarantee a
# next unnamed one. THE INVARIANT the whole mechanism serves: the probe
# consults nothing outside the throwaway repository and the file under
# test -- clearing environment variables and setting config values
# explicitly are both just ways of holding that invariant, and it is what a
# new git call added here should be checked against, not the list of
# vectors found so far (which is empirical enumeration, not a claim of
# completeness). Negation detection asks git directly rather than guessing
# which spellings might apply or assuming a companion pattern exists. The
# writer reports this as "has a '!' negation on file", not as a
# verified "already un-ignored" claim: it reflects only THIS file's own
# effect at the moment it ran, not full multi-source gitignore precedence
# (nested .gitignore files, global excludes), and a later broader ignore
# pattern in the same file (e.g. `work-items/**`) can still re-ignore the
# tree after it. The throwaway repo is always removed before the writer
# returns, including on an interrupt, abort, or hung git (a bash EXIT-trap
# chained onto whatever trap the calling installer script already has
# registered; a PowerShell `try/finally`).
#
# Case sensitivity is NOT uniform across the two decline mechanisms, and this
# is deliberate:
#   - The sentinel is OUR OWN machine token -- we define its form, so it is
#     case-SENSITIVE on both engines (bash `grep -Fxq`, PowerShell
#     `-ccontains`), everywhere, regardless of the target repo's git config.
#   - A `!entry` negation is GIT's OWN syntax, so GIT's own rules apply,
#     including its own `core.ignorecase`-governed case sensitivity (git
#     itself writes this into `.git/config` as `true` at init/clone time on a
#     case-insensitive filesystem -- typically Windows/macOS -- and leaves it
#     unset, which behaves as false, on a case-sensitive one -- typically
#     Linux). The throwaway repo used for negation delegation mirrors the
#     TARGET repo's own explicit LOCAL `core.ignorecase` when one is set
#     (read with `--local`, never plain `config`, which falls through to
#     global/system config even from inside a repo with no local override --
#     confirmed this session that omitting `--local` can leak an unrelated
#     global override into a non-repo install's decision), falling back to
#     its own filesystem auto-detection only when the target has no such
#     override -- so a differently-cased negation OR a differently-cased
#     bare positive pattern git itself would honor is never silently
#     destroyed by a fixed-case writer policy, in either direction. If `git`
#     itself is unavailable, the writer leaves every undetermined tier alone
#     with a distinct disclosure message rather than falling back to a
#     spelling guess -- the very mechanism this round retires. This
#     reasoning is not duplicated elsewhere; the installers' own inline
#     comments point back here.
#
# One tier per line, leading slash form (as written into .gitignore).
