- **Anti-hardcoding and justified limits:** do not hardcode machine/user/repo-layout/environment-specific, secret or policy-owned values when accepted constants/config/parameters/env/discovery suffice; shared artifacts use repo-relative/documented forms. True invariants/protocol constants/small algorithm literals allowed; surface tradeoff first. Before changing classify: invariants/protocol/schema may stay fixed; policy defaults need one owner/omission safety; deployment/calibration/user inputs need variability/omission tests. Do not impose limits on count, size, depth, duration, iterations or evidence merely for convenience, labels or unexplained defaults; justify them by an actual external contract, algorithm invariant, evidenced reachable risk or accepted resource budget. Explain the owner, scope, units, value/default and reason in the existing engineering work or review, including required function, evidence retention and safe overflow behavior; prefer bounds derived from valid inputs or owned configuration when variable, without arbitrary refusals, silent truncation or masked degradation. Preserve justified safeguards, host restrictions and acquired outcomes; reassess existing limits implicated by the task or observed failure, without a universal constants rewrite or a new artifact, approval or gate.
- **No logic duplication / no fix layering:** keep one coherent current truth; no duplicate logic/fixes. A clarification that changes a live textual artifact's meaning supersedes its prior wording: replace stale prose; history in Git/designated decision/closure record. Keep both only for genuinely cumulative and non-conflicting detail. Update canonical owner in same change; unclear: name gap/update narrowest confirmed surface. Repeating a decision or check over unchanged authoritative inputs without a distinct responsibility is redundant; independently required validation of a boundary contract or current state is not duplication and retains the same policy owner; defense-in-depth needs untrusted/corruptible boundary, agreed thresholds and commit justification. SECOND same-session fix breaking a working neighbor: STOP all edits; diagnose owner/siblings/shared contract.
- **General-case over local symptoms:** find the correct concept/abstraction level and owner/siblings (modes/surfaces/inputs/timing). Same cause -> owner-level general case; smallest coherent seam; interfaces/coordination inside; state wider coupling and preserved/generalized invariant in commit. Avoid incidental data structures: give meaningful wholes an object owning parts/relations/invariants/lifecycle; reuse existing owners; introduce a representation or seam only when it owns a required responsibility or protects a justified boundary, rather than merely reboxing data. Broad impact: seam suspicion; SOLID pressure test only. Choose correctness over development speed unless explicit prototype/fastest/throwaway. Special case: explicit user-approved boundary; broader cases left untouched with verified/out-of-scope rationale. Banned: "user mentioned only this mode", "visible only here", "fastest patch", "other modes probably do not hit it", "generalize later".
- **Directory-level entity separation:** group source by primary entity + ownership/lifecycle, not extension/language/name. Narrative/grandfathered exceptions: `shared/references/repository-source-hygiene.md`.

No half-finished alternatives/dead helpers/stale docs/"TODO: remove later" beside live code.
