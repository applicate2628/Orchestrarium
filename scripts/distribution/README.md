# Orche distribution boundary

`build.py` owns local payload assembly. `launch.py` owns bundle-relative resolution,
Python environment isolation, and explicit create-only retention. `install.py`
owns client selection and delegates unchanged pack policies to the existing Python
installer. Shell/PowerShell entry files generated by the builder only locate this
runtime; they do not acquire payloads or implement install/update/rollback policy.

POSIX uses process replacement for the bundled entry. Windows starts the selected
absolute Python with an argument sequence and no shell, waits for it, and returns
its actual exit status. This preserves spaces/Unicode and avoids the Windows CRT
`execve` quoting/overlay behavior. It is not a new hostile-process containment claim.

## Current installation model

Selected clients receive independent ordinary copies. New installations do not
use a shared skill directory or client-to-client projection links. Explicit legacy
migration converts only the selected client's historical links; uninstall uses
that client's ownership records and must not remove another client's files.

The symbolic-link qualification below is historical evidence and remains relevant
to legacy restoration paths. It is not a requirement to create links in a fresh
copy-based installation, nor evidence that the final internet distribution is
qualified. The retained interpreter lifetime is a separate concern: registered
hooks may still reference it, so removing client copies does not authorize runtime
garbage collection.

## Current reproducibility record

`locks/linux-x64-cp315.txt` freezes the 41 binary wheels actually tested on Linux
x64 with normal-GIL CPython 3.15.2. Its companion sources JSON records the exact
wheel URLs and SHA-256 values from the package resolver. This is a platform-specific
qualification input, not a floating upgrade policy or a universal requirements file.
Use `python -m pip install --require-hashes --only-binary=:all: -r <lock>` when
preparing an isolated, verified runtime. The local builder does not run pip.

`locks/windows-x64-cp315.txt` records the corresponding Windows x64 resolution:
42 installed binary wheels, including the Windows-only `pywin32` dependency.
Its sources JSON also records the normal-GIL CPython 3.15.2 Windows standalone
archive URL and checksum. Runtime assembly, import, and launcher checks do not
by themselves qualify actual client installation or native hook trust.

## Evidence and release holds

- Local shared-launch/selection/build/retention tests use synthetic runtimes where
  indicated; those do not establish executable provenance or OS support.
- A real Linux no-hook install and reapply succeeded using retained Python with
  unavailable ambient PATH/PYTHONHOME/PYTHONPATH, after moving the original bundle
  out of its source location. A user marker survived reapply.
- Earlier SDK collection under actual Python/SDK libraries: 1182 passed, 5 skipped,
  71 subtests. Two official source-fixture cases passed separately. These counts
  do not establish live provider calls, full repository green, or new Windows tests.
- Final focused projection/producer and launcher/build/selection checks on elevated
  Windows: 122 passed and 101 subtests passed. The earlier unelevated launcher-only
  run had 39 passes and six symlink-privilege skips; those are not additive counts.
  The same final scope on Linux has 118 passes, four Windows-only skips and 101
  subtests. Tests cover argument boundaries, child failure status, native rollback,
  nested thread-token restoration, an unchanged process token, refusal to grant a
  missing effective privilege, and process termination if identity restore fails.
- A rebuilt Windows retained bundle installed and reapplied both clients without a
  diagnostic privilege wrapper after moving its acquisition directory. All 54
  Claude skill projections were accessible and a user marker was preserved.
  This was an elevated account with an existing symlink privilege, not proof of
  unelevated installation. Windows hook-enabled qualification remains open; macOS
  is documentation/static only. Target tuples are layout choices, not declarations
  of qualification.
- Remote release authentication, download/extraction protections, license inventory,
  inventory-driven runtime minimization, npm/irm/sh acquisition, and final product
  version/tag selection remain release gates. Do not publish this as a completed
  internet installer. Checksums alone are not publisher authentication.
- Retention is explicit and refuses existing destinations. Incomplete copies remain
  for diagnosis; no pack installer starts until assembly completes. Existing retained
  releases are not garbage-collected because registered hooks can still use them.

## Local ownership and runtime lifetime

Apply requires an explicit first launcher option: `--retain-to ABSOLUTE_DIRECTORY`
or `--permanent-runtime` for an already permanently placed bundle. Retention
re-executes the retained launcher with that explicit lifetime decision; repeated
apply uses `--permanent-runtime`. Listing, help and dry-run do not need it. This
records operator intent, not a promise that a directory can never be deleted.

Use verified, quiescent source/runtime trees and an exclusively controlled output
parent hierarchy for the whole build, retention and launch. Static aliases and
Windows reparse points in roots/parents are refused before normalization. Payload
symlinks observed by the copy operation are preserved and validated before the
manifest is written. The regression covers a leaf swap before copy2's link check;
it does not cover a swap between that check and open. Any concurrent leaf or
ancestor replacement, including ABA races, is outside this local contract. A
stronger contract would require descriptor/native-handle-bound acquisition and
publication. No authenticated remote extraction or
shared writable staging-directory use is admitted by these local checks.

## Windows native symbolic-link privilege

The native creator requires `SeCreateSymbolicLinkPrivilege` at handle acquisition.
Elevation alone may leave it disabled. For symlink creation/restoration the installer
duplicates the current effective token, enables only that already-present privilege,
and scopes the duplicate to the calling thread. It never changes the process token,
grants a missing privilege, or changes Windows policy. Prior thread impersonation is
restored on success and ordinary failure. Failure to restore identity terminates the
installer with exit 70; it cannot safely continue rollback in an unexpected context,
so retained transaction state requires inspection. Standard-user support is not
established by the elevated tests; junction fallback is not shipped.

API references: [FSCTL_SET_REPARSE_POINT](https://learn.microsoft.com/en-us/windows/desktop/api/winioctl/ni-winioctl-fsctl_set_reparse_point),
[AdjustTokenPrivileges](https://learn.microsoft.com/windows/win32/api/securitybaseapi/nf-securitybaseapi-adjusttokenprivileges),
and [impersonation restoration failure](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-reverttoself).
